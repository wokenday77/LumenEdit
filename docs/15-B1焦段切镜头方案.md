## 零、一句话结论

**切镜头不需要重建会话。** 设备回退链本来就是**虚拟多摄优先**（`.builtInTripleCamera` 起），
系统会在 `videoZoomFactor` 越过切换点时**自动换 constituent 镜头**且画面平滑
（`CaptureCapabilities` 的注释里当初就写了这个理由）。

所以 B1 = **把"档位 → zoomFactor"算准 + 用 `ramp` 平滑过去 + 界面接线**，
**全程不增删 input/output、不 `beginConfiguration`**。

## 二、`Ramp` 的具体用法（iOS 18 `AVCaptureDevice.Ramp`）

Apple 文档的三条硬事实：

1. **必须在 `lockForConfiguration()` 之后调用** —— 否则抛 `NSGenericException`
   → 与本项目**铁律 2**天然吻合：**ramp 也只在 `CaptureDeviceConfigurator` 里做**，
   也就是说"唯一锁"这条纪律帮我们自动避开了这个坑。
2. **`rate` 的单位是"每秒 2 的幂次"**（powers of two per second）：`1.0` = 每秒翻倍/减半；
   **只取绝对值，方向由目标值自动决定**；`rate = 0` 等价于 `cancelVideoZoomRamp()`。
3. **给 `videoZoomFactor` 赋值会打断进行中的 ramp 并直接跳到新值** ——
   连点档位时不需要先 cancel（直接再调 ramp 即可），但也意味着"别在 ramp 途中手贱赋值"。

### 签名：**只有 `withRate:` 一种**（Mac 侧 2026-09-19 读 iOS 26 SDK 实测 · 已落地）

Mac 侧读了本机 iOS 26 SDK 的 `AVCaptureDevice.h` —— 整个 VideoZoom 分类**只有三个 API**：

```objc
- (void)rampToVideoZoomFactor:(CGFloat)factor withRate:(float)rate;   // 返回 void
@property(readonly) BOOL rampingVideoZoom;
- (void)cancelVideoZoomRamp;
```

**没有 `withDuration:` 重载，也没有 `AVCaptureDevice.Ramp` 类型。**

> ⚠️ 本节原先写的是"若存在 `withDuration:` 重载则**首选**"，并据此让实现用
> `_ = device.ramp(...)` 去兼容"返回 `Ramp` / 返回 Void"两种签名 —— **那个前提不成立，已删除**。
>
> 教训记一笔：**"两种签名都能编译"这种兼容写法本身是有前提的**（得先确认真存在第二种签名）。
> 前提没核实就写，它只是把"签名不确定"这件事**藏起来**，反而让人以为已经处理完了 ——
> 与本项目在 `AVCaptureEventInteraction` 上那次的性质相同，但那次至少还标了"待确认"。

### 固定时长怎么实现（既然只有 `withRate:`）

`rate = log2(target / current) / 期望时长`，期望时长取 **0.35s**
（`CaptureDeviceConfigurator.zoomRampDuration`）。这样"13→24mm"与"13→120mm"
**视觉上差不多快**（固定 rate 的话跨档越大越慢：13→120 要 `log2(9.23)/3 ≈ 1.07s`，太久）。

**调手感只改这一个常量** —— 调用处无处可传时长（没有 `withDuration:`）。
自检第 11 组⑧守着它的量级 ∈ `[0.2, 0.6]s`、且 `rate` 必须由 `log2` 算出。

| | 现有 `applyZoomLocked` | B1 新增 `applyZoomRamp` |

  含既有的"max 可能为 0/非正"防护
- ⚠️ **不要动 `applyZoomLocked` 的语义**：`CapturePreset.zoomFactor` 与"焦段档位"是**两套来源**

  否则将来 P4 注入预设时会出现"两个来源抢 `videoZoomFactor`"。

## 四、档位 → 镜头/变焦怎么映射（**按镜头角色从设备读** · 2026-09-19 重写）

> ⚠️ **本节第一版（"等效焦距 ÷ 基准"，基准写死 13mm）已被真机实测推翻，作废。**
> 下面保留反证过程，避免有人再把它改回去。

### 实测反证（Mac 侧 2026-09-19）

某机 `virtualDeviceSwitchOverVideoZoomFactors = [2.000, 10.000]`。反推：

```
2.0  × base = 24mm  →  base = 12mm
10.0 × base = 120mm →  base = 12mm    ✓ 自洽
```

即**这台设备的虚拟基准是 12mm，不是 13mm**。后果两层：

| # | 后果 | 严重度 |
|---|---|---|
| 1 | `mm ÷ 13` 整表偏小约 **8%**（24 → 1.846 而非 2.0；120 → 9.231 而非 10.0） | 中 |
| 2 | **120mm 档算出的 9.231 落在 `switchOver[1] = 10.0` 之下** → 系统**不会切到长焦**，只会继续用主摄数码放大（糊），而 UI 显示"已切到 120mm" | 🔴 高 |

第 2 条正是本项目明令禁止的"**装作切过去了**"。

### 新做法：按**镜头角色**读设备（基准之争就此消失）

```
原生阶梯  nativeZooms = [1.0] + virtualDeviceSwitchOverVideoZoomFactors
          （第 i 项 = 第 i 颗 constituent 的原生视场；1.0 = 最广那颗，Apple 文档 full field of view）

13mm   → 超广角的原生视场            = 阶梯第 0 级 = 1.0
24mm   → 广角的原生视场              = switchOver[0]
35mm   → 广角的原生视场 × 35/24      = switchOver[0] × 1.4583  （主摄数码裁切）
48mm   → 广角的原生视场 × 48/24      = switchOver[0] × 2       （主摄 2× 裁切 = 48MP 传感器裁切点）
120mm  → 长焦的原生视场              = switchOver[last]
```

> 35 与 48 共用同一条式子「**主摄原生 × 标称比例**」，比例 = `标称 mm ÷ 24`
> （`FocalPreset.mainCropFactor`）—— 比在一处写死 `×2` 更难改坏。
> 详见 `docs/17`（加 35mm 档的方案与确认记录）。

| 档位 | 角色（`FocalLensRole`） | 实测那台机（switchOver `[2.0, 10.0]`） |
|---|---|---|
| 13mm | `ultraWide` | **1.000** |
| 24mm | `wide` | **2.000** == `switchOver[0]` ✓ |
| 35mm | `mainCrop`（×35/24） | **2.917**（落在 `switchOver[0]` 与 `switchOver[1]` 之间 → 不换镜头） |
| 48mm | `mainCrop`（×2） | **4.000** |
| 120mm | `telephoto` | **10.000** == `switchOver[1]` ✓ **落在长焦上** |

> ⚠️ 比例里的 `24` 是**标称基准**（`AVCaptureDevice` 不暴露镜头的绝对等效焦距）。
> 用户那台机主摄确实是 24mm ⇒ 35mm 档恰好等于 35.0mm；若某机型主摄是 26mm，该档实际约 37.9mm。
> 这套标签本来就有此前提；**B1 那次事故的错在锚点（把基准当成 13），不在标签**。

**为什么这样更好**：`12mm 还是 13mm` 这个问题**不再需要回答**；而且"哪几档可用"顺带由设备自身的
镜头构成决定（阶梯长度 = 镜头数 − 1）。

### 可用性（顺带把置灰判据也解决了）

| 设备 | 原生阶梯 | 13mm | 24mm | 35mm | 48mm | 120mm |
|---|---|---|---|---|---|---|
| 三摄（超广角+广角+长焦） | `[1.0, s0, s1]` | 1.0 | s0 | s0×1.458 | s0×2 | s1 |
| 双摄宽（超广角+广角） | `[1.0, s0]` | 1.0 | s0 | s0×1.458 | s0×2 | **不可用**（无长焦） |
| 双摄（广角+长焦） | `[1.0, s0]` | **不可用**（无超广角） | 1.0 | ×1.458 | ×2 | s0 |
| 单广角 | `[1.0]` | **不可用** | 1.0 | ×1.458 | ×2 | **不可用** |

> 35mm 那一列**四种配置下都可用**：它只需要主摄（每台都有），而 `2.917 < 4.0`
> ⇒ "48mm 能用 ⇒ 35mm 一定也能用"。它是这一族里最宽松的一档。

实现：`CaptureCapabilities.zoomFactor(forFocal:of:)` —— 设备没有那一档需要的镜头时返回 `nil`，
由 `unavailableFocalIds` 判为不可用（**灰 + 仍可点 + 点了给 toast 说明原因**）。

**镜头探测（两条互补，任一命中即可）**：

| # | 判据 | 为什么需要 |
|---|---|---|
| ① | `device.constituentDevices` 各 constituent 的 `deviceType` | 最准 —— 它说的就是"**当前这台设备**"里到底有哪几颗 |
| ② | `DiscoverySession(deviceTypes: [那颗镜头], mediaType: .video, position: .back)` 有没有结果 | **兜底** —— `constituentDevices` 只在虚拟设备上有意义；一旦回退到物理设备（或某些系统版本上对非虚拟设备返回空数组），① 会**漏判** → 该档不置灰 → 用户点了画面不动 |

- 角色与阶梯**按下标配对**，配对前把角色按"最广 → 最长"**显式排序** ——
  这样就不依赖"Apple 返回的数组顺序是否也从广到长"这个本机（无 Xcode）验证不了的前提。
- `constituentDevices` 为空时按能力探测**重建**角色表 —— 只信 `deviceType` 会把"三摄但列表为空"
  误判成单摄 → 13mm 与 120mm 两档被无谓置灰。
- 角色数超过阶梯长度（系统没给切换点）→ 判**不可用**（宁可不给，也不装作切过去）。

> ⚠️ **绝不能用 `caps.zoom.min` 当判据**：单广角回退机型上它同样是 **1.0**，
> 区分不了 "1.0 = 最广视场" 还是 "1.0 = 广角视场"。

### 核法（已升级，取代原来的"设 1.0 拍一张、与相册 13mm 对比视场"）

会话配置完成时打一行**变焦拓扑**日志，把上面这笔账变成**可当场核对**的硬数据：

```
变焦拓扑：deviceType=… · constituents=3 · 角色=[超广角,广角,长焦] ·
  switchOver=[2.000, 10.000] · 原生阶梯=[1.000, 2.000, 10.000] ·
  档位=13→1.000 / 24→2.000 / 48→4.000 / 120→10.000 · 不可用=无 · zoomRange=[1.00, 15.00]
```

判读口径：`13mm 档 == 1.000`、`24mm 档 == switchOver[0]`、**`120mm 档 == switchOver[last]`**。

### 能力不足时的降级（诚实边界，不做"点了没反应"）

| 情形 | 处理 |
|---|---|
| 目标 zoom > `maxAvailableVideoZoomFactor` | clamp 到 max + toast：`该档超出本机能力，已用 xx 倍` |
| 设备没有超广角（13mm 档不可用） | **置灰该档** + 点它给 toast 说明（产品约束：未实现必须置灰 + 说明原因） |
| 设备没有长焦（120mm 档不可用） | 同上 |

置灰需要 UI 侧一个输入：`FocalStripView` 增 `unavailableIds: Set<String>`（默认空 → 不影响现有调用点）。
**建议一起做**（成本低、守产品约束），若要控制本件范围也可只做 toast —— **请拍板**。
> **已拍板并落地**：做了置灰（灰 + 仍可点 + 点了给 toast），见第七节⑦与第九节第 7 条。

### 前置模式下的行为（2026-09-19 按 Mac 侧预检补齐）

**当前状态：前置切换还没交付。** 图标行第 1 项「前置」只给 toast
（"前后镜头切换要重建会话输入，在 P2 硬件批次交付，当前固定后置"），
所以**现在根本不存在"切到前置"的路径**，B1 的四档映射不需要为前置加特例。

**但口径现在就要定下来**（防后人接前置时踩坑）：

| 项 | 口径 | 现在就已经成立的部分 |
|---|---|---|
| 镜头角色 | 按**当前设备**重新探测 —— 前置通常没有超广角/长焦 → 13 / 120mm 档多数不可用 | `constituentRoles(of:)` / `unavailableFocalIds(for:)` 都是**吃 `device` 参数的纯函数**，天然跟着设备走 ✓ |
| 档位可用性 | 预期 13 / 48 / 120mm **多数不可用** → 置灰，点了给 toast 说明 | 复用 `unavailableIds` 那一套 ✓ |
| 何时重算 | 换镜头必然重建 input → 会话重建 → `startInternal()` 里 `unavailableFocalIds = CaptureCapabilities.unavailableFocalIds(for: device)` 会**重算一次** | 已在"配置完成"处计算 ✓ |
| 选中态落在不可用档 | 会话就绪后**不推硬件**，保持设备默认视场（UI 那边本来就置灰） | `reapplyFocalAfterSessionReady()` 已有该守卫 ✓ |
| **还需拍板的** | 前置下焦段条是**整条隐藏**还是**保留 + 全部置灰**？直觉上前置用户不切焦段，但那是产品决定 —— **留给接前置（后续 B 件）时拍板**，本件不预判 | ⬜ |

> **结论：B1 不需要为前置加特例** —— 映射与置灰本来就是"按当前设备算"的。
> 真正要防的只有一件事：**有人把探测结果缓存成常量**（那样换镜头后 13mm 档会一直显示可用）。
> 自检第 11 组① 守着这段映射（角色表必须逐条精确、原生阶梯必须是 `[1.0] + switchOver`、
> 档位必须严格单调、**且不许再有 `mm ÷ 基准` 的残留**），谁把它改成常量或改回除法会当场报出来。

## 五、会话稳定性（你特别问的一点）

**B1 完全不碰 session 图。** 对比一下两条路径：

| 路径 | 做什么 | 代价 |
|---|---|---|
| **模式切换**（照片↔视频↔Log） | `beginConfiguration` → **增删 output** → `commitConfiguration`（`reconfigureOutputsLocked`） | 重建输出图，有可感知停顿 |
| **B1 切档位** | `lockForConfiguration` → `ramp` → `unlockForConfiguration` | **不动 input/output、不 beginConfiguration**，系统内部换 constituent |

- 也就是说：**用户问的"参考模式切换动态增删 output 的做法"在这里不需要用** ——
  那套做法是给"采集图真变了"用的；切镜头时采集图没变（同一个虚拟设备、同一个 input）
- 安全保障来自现有架构：所有设备配置都在 `sessionQueue` 上**串行**执行
  → 不会出现"ramp 播放中又去 `beginConfiguration`"
- ⚠️ **录制中允许变焦**（系统相机支持，`videoZoomFactor` 与录制正交）→ 但列为真机验证项，
  异常的话加"录制中禁用档位切换 + toast"

### 补充：会话就绪后必须"按档位对齐一次"（实现时发现）

配置阶段的变焦只认 `CapturePreset.zoomFactor`（预设注入链路），而 **UI 的真相是"焦段档位"
（默认 24mm）**。两者不是一个来源 → 不对齐就会出现：

> **冷启动后画面是 13mm 超广角视场（设备默认 1.0），但焦段条选中态写着 24mm**。

所以新增 `CameraViewModel.reapplyFocalAfterSessionReady()`：订阅 `session.$state`，
变成 `.running` 时按当前档位 apply 一次，**且用非动画**（会话刚就绪不该让用户看到画面推近一下）。
不可用档位（置灰的那些）不推硬件，保持设备默认视场。

> 这条与第三节"不动预设链路"不冲突：预设链路仍然决定**配置阶段**的初始 zoom，
> 只是就绪后由"焦段档位"（UI 真相）覆盖一次。等 P4 把两者统一（`EditRecipe` 驱动）后，
> 这个覆盖动作可以撤掉。

## 六、触控热区

**现状已达标，B1 不改**：药丸**视觉** 44×30、**命中高 44**（`FocalStripView` :89-91，
上下各借 7pt 是**条内空白**，不侵占任何控件）；横向 44pt 本身 ≥ HIG 下限。
唯一相关改动是"不可用档位置灰"（若拍板做），**热区不变**。

## 七、自检增强（`tools/check_swift.js` 第 11 组 · 现 **14 条**）

| # | 检查 | 为什么 |
|---|---|---|
| ① | 档位按**镜头角色**从设备读：档位数 = **5**、角色表逐条精确（13→ultraWide / 24→wide / **35、48→mainCrop** / **120→telephoto**）、原生阶梯 = `[1.0] + switchOver`、裁切档必须用 `mainCropFactor`、角色超阶梯判不可用、**且无 `mm ÷ 基准` 残留**；并在真机实测配置（三摄 `[2.0, 10.0]`）上复算 —— 严格递增 + `24mm == switchOver[0]` + **`120mm == switchOver[last]`** | 第一版"`mm ÷ 基准`"被真机推翻（基准是**机型相关**的，实测 12mm）→ 120mm 档算出的 9.231 落在 `switchOver[1] = 10.0` 之下、系统不切长焦只数码放大。这条是那次事故的**回归守卫**（见第四节）。⚠️ 正则**必须支持 `case 35, 48:` 这种合并写法** —— 不能让 Swift 迁就检查脚本（踩过一次假 FAIL） |

| ② | 用 `ramp(toVideoZoomFactor:` 而不是硬设 `videoZoomFactor =` | 硬设是"跳"，本件的意义就在平滑 |
| ③ | **`ramp` 只出现在 `CaptureDeviceConfigurator.swift`** | 铁律 2：唯一锁的地方才能做设备配置 |
| ④ | clamp 到设备能力（`minAvailableVideoZoomFactor` + `videoMaxZoomFactor`） | 越界赋值是**抛异常**，不是被忽略 |
| ⑤ | 新方法体内**不得出现** `beginConfiguration` / `addInput` / `removeInput` | "切镜头不重建会话"是本件的核心不变量 |
| ⑥ | 焦段条命中高仍为 `Theme.Size.focalStripHeight`（44） | 防被改回"药丸高 30"（那会掉到 HIG 下限以下） |
| ⑦ | （若做置灰）`FocalStripView` 有 `unavailableIds` 且不可用档位**仍可点**（给原因） | "点了没反应"与"灰了但没解释"都不允许 |
| **⑧** | **量级守卫**：`rate` 必须由 `log2` 算出，且 `zoomRampDuration ∈ [0.2, 0.6]s` | 沿用 `docs/11` 第七节的判据「**机制在但量太小等于没做**」。太小 ≈ 硬跳（本件的意义没了）、太大 ≈ 拖沓 |
| **⑨** | **双来源守卫**：`applyZoomRamp` 与 `applyZoomLocked` **不得互相调用**，且配置期那条仍必须是硬设 `videoZoomFactor =` | 两者口径不同（焦段档位 vs `CapturePreset.zoomFactor`）。互相调用 → P4 注入预设时"两个来源抢 `videoZoomFactor`"，画面来回跳且极难归因 |
| **⑪** | **裁切档系数同源**：`FocalPreset.mainCropFactor` 必须是 `return mm / 24`（式子必须在），且 `CaptureCapabilities` 必须用它（不许写死倍数）；复算 35→1.4583 / 48→2.0 | 35 与 48 是同一类（主摄内裁切）。一处写 ×2、另一处写 1.46 = "两个来源"，必然只改一处。加 35mm 档时新增 |
| **⑫** | **焦段条宽度预算**：令牌**真读**（`focalPillWidth` / `focalStripSpacing` / `Spacing.md`）+ `CameraView` 的水平内缩假设仍在；对 402/393/390/375 **四机型逐档复算**余量，并算出**最窄机型的档数硬上限** | 加档位才有横向溢出风险，而**此前自检里一条焦段条宽度检查都没有**（第 5 组只管顶栏与图标行）—— 这是个盲区。做法与第 5 组一致 |

| **⑭** | **声明式扩展（只做本地一致性）+ 每档都要能解析出角色**：`isSwiftExtension: Bool = false` 字段必须在且默认 `false`；`isSwiftExtension: true` 只允许出现在 `FocalCatalog` 的档位构造行里；**`FocalCatalog` 每一档都要在 `lensRole` 的 switch 里有 case**。⚠️ **不要求"至少有一处扩展"**（0 个扩展 = 原型已同步 = 健康状态） | 最后一条最要命：新加一档却忘配角色 → `lensRole` 返回 nil → `zoomFactor` 返回 nil → **该档永远置灰且点不出原因**（静默的"点了没反应"）。<br>⚠️ 初版写成"至少要有一处扩展"，被 CB 抓出会在原型补齐后把**健康状态判成 FAIL**（两边打架）→ 已修正，详见 `docs/17` 第十一节 ② |

## 八、风险与回退

| 风险 | 处理 / 回退 |
|---|---|
| `ramp` 签名不确定 | 用 `_ =` 兼容写法；真机报错按 Xcode 自动补全改一行（既有做法） |
| `1.0 = 13mm` 的前提不成立 | 映射表整体平移（改 4 个常量），其余逻辑不动 |
| 连点档位 | 直接再 ramp（文档说赋值会打断 ramp，重新 ramp 即换目标）；视觉上是"改向加速"，可接受 |
| 录制中变焦异常 | 加"录制中禁用 + toast"；实现位置在 `CameraViewModel.focalTapped` 一处 |
| 降级路径（clamp）让"档位与视场不符" | **必须 toast 说明**，不装作切过去了（诚实边界） |

## 九、验收清单（真机）

1. 点 13 / 24 / 48 / 120mm → 画面**平滑推近/拉远**，无跳帧、无闪黑
2. 13mm ↔ 120mm 往返 → 两个方向**耗时接近**（约 0.35s）
3. 跨镜头切换点（约 2x、9.2x）→ **构图不跳**（口径已放宽：换 constituent 的瞬间，**亮度 / 对焦**变化可接受，
   只要画面不整体位移、不闪黑）
4. 连点不同档位 → 不崩、最终停在**最后点的档**、选中态与画面一致
5. **录制中**切档位 → 正常，回放能看到变焦
6. 切档位后**拍照** → 照片视场角与取景器一致（zoom 真生效）
7. 档位不可用（若设备无超广角/长焦）→ **置灰 + toast 说明**（或按拍板结果只 toast）
8. 模式切换（照片↔视频）后再回来 → 档位选择保留、变焦值正确
9. 变焦过程中接**拍照** → 不崩、照片取当前 zoom
10. **冷启动日志有一行「变焦拓扑」**（② ④ 的新核法，**替代**原来的"设 1.0 拍一张、与相册对比视场"）：
    应为
    `变焦拓扑：deviceType=… · constituents=N · 角色=[…] · switchOver=[…] · 原生阶梯=[…] · 档位=13→… / 24→… / 35→… / 48→… / 120→… · 不可用=… · zoomRange=[…]`
    核对三件事：
    - `13mm 档 == 1.000`（最广 constituent 的原生视场）
    - **`24mm 档 == switchOver[0]`**（广角原生视场）
    - **`120mm 档 == switchOver[last]`** —— 这条是 B1 第二次修订的**命门**：小于它说明系统不会切长焦，
      只会主摄数码放大（旧算法正是踩在这里）
    ✅ 不用动相机、不用人工判断视场，**读一次日志就有硬数据**。
    加 35mm 档之后的**五档验收清单见 `docs/17` 第十节**。
11. **会话就绪日志同一帧只打一遍**（2026-09-19 修）：`会话就绪 · 焦段 24mm 已对齐（变焦 …）`
    此前会打两遍（根因：`startInternal` 冷启动走两次 + `.running` 同值重发）。

## 十、本件的边界（不做）

- **捏合手势连续变焦**（pinch）→ 不在本件（另一套交互，且与档位切换要协调）
- 焦段与 `CapturePreset.zoomFactor`（预设链路）统一 → 等 P4
- 变焦台阶/focal 曲线（`Ramp` 的 rate 自适应）→ 先固定 0.35s，真机手感再调
