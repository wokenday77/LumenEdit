## 〇、先看结论（拍板点都在这）

## 二、改动点（文件 / 函数 / 时机）

### 2.1 档位 → 设备格式（**新增只读查询**，放 `CaptureCapabilities`）

- `resolveVideoFormat(device:resolution:frameRate:) -> AVCaptureDevice.Format?`
  - 尺寸：720p = 1280×720、1080p = 1920×1080、4K = 3840×2160 —— **按 min/max 归一比较**（竖拍格式存在，别写死宽高顺序）
  - 帧率：该格式 `videoSupportedFrameRateRanges` 中存在能容纳所选 fps 的 range（`CMTimeRangeContainsTime`）
  - 多候选：① 优先 `maxFrameRate` **恰好等于**所选 fps 的格式；② 仍并列 → **复用探测那套优先序**（`420v` 优先 + 面积降序）⇒ 不新立第二套口径
- `availableVideoFormatMatrix(device:)` → 3×4 可用矩阵（驱动 UI 置灰）
- `videoFormatKind(of:) -> (VideoResolution, VideoFrameRate)?`（**反解**，与上同一张尺寸表 ⇒ 单一真源）；反解不出（设备给慢动作专用格式等）→ nil，UI 回落显示 `formatSummary` 原始描述
- ⚠️ **能力探测与将要执行的写入逐字对应**（坑 #9）：判据只用 `device.formats` + `videoSupportedFrameRateRanges`，不得用近似 API 替代
- ⚠️ 三条都是**纯查询**（不写设备）；真正的写入仍只走 configurator

### 2.2 会话层新入口（**唯一写路径仍经 configurator**）

`CaptureSessionController` 新增 `requestVideoFormat(resolution:frameRate:)`，全程在 `sessionQueue`：

1. **录制中 → 拒绝**（复用既有"录制禁切"闸门 + toast），不排队、不静默；
2. **未就绪 → 记"待应用目标"并用回执触发**（复用"排队补执行"；⚠️ 坑 #15：**不许盲等超时**，"已就绪"要有单独回执）；
3. **就绪 → 解析格式**（2.1）：
   - 解析不到 → **不写**、状态回滚、toast"该组合本机不支持"（铁律 5：不做"点了没反应"）；
   - 解析到 → `configurator.applyFormat(format, frameRate: 所选fps, to: device)`；
4. **写完立刻复查并补写手动档**（`reverifyManualIntent`）—— `activeFormat` 一变，ISO/曝光域就变（坑 #14 同族），**不能省**；
5. **发布实际生效档位** `appliedVideoFormat`（反解）→ 供芯片显示 + 日志；
6. **留痕一行**：`视频格式已应用：<档位>（applyFormat 1 次，耗时 X.XXs）` —— 这就是 Mac 的核验判据。

### 2.3 UI 侧

- `FormatChipView`：档位按矩阵**置灰 + 点了给 toast 说明原因**（第 10 组"档位齐全"守卫同步升级为"置灰来自设备探测"）；
- `CameraViewModel`：
  - `formatResolutionTapped/FrameRateTapped` 改为"改状态（落盘不变）+ `session.requestVideoFormat(...)`"，toast 去掉"属 B 组"；
  - **过渡态**：目标 ≠ 实际时芯片显示**实际值** + 轻提示（"正在切到 4K · 60"），落地转正；**不许长时间只有目标值没有实际值**；
  - `formatChipText` 改读会话已发布实际格式（落地 `:174-179` 的 TODO）；未就绪时回落目标值并标注"待生效"；
  - `storageChipText` 用**生效码率**（见 2.4）；
- `TopBarView`：**不动**（预留宽度已处理）。浮层互斥 / 放大态：**不动**。

### 2.4 码率（"设备推荐值"怎么落地）

| 路线 | 做法 | 判断 |
|---|---|---|
| **R2（推荐）** | **实测回填**：每次录制结束读成片 `AVAssetTrack.estimatedDataRate` → 作为该 (设备,分辨率,帧率) 的**实测量**落盘；下次估算优先实测、无则占位表 | **零 API 风险**、自校正、天然诚实 |
| R1（升级项） | 读系统推荐码率（候选 API 见 §5） | **存在性未定** → 先让 Mac 查头文件；存在也不改静态表，只作运行时优先来源 |
| R3（兜底） | 保留占位表，把文案从"按码率估算"改为"按估算码率（占位）" | 最省，但估算永远不准 |

→ **建议 R2 为主**（R1 查证后叠在前面）；**静态占位表一律不回改**。

### 2.5 作用域：手动选择 ↔ 探测缓存（**决定"会不会污染实况 / Log 实况"**）

- 现状：格式由探测决定，缓存 **key 含模式**（每个模式的格式分开）。
- 规则（建议）：**用户选择只作用于"当前会话形态"，同时落盘为该形态下次的"首试目标"** —— 冷探测/换设备时把用户选择**排在候选最前**，仍由探测**验证**它（含 Live 判据）：
  - 通过 → 用它（用户意图生效且 Live 安全）；
  - 不通过 → 自动回落探测结果 + toast ⇒ **绝不把手动选择直接灌进 Live 相关模式**。
- 副产品：**"切模式后格式回到默认"的观感问题一起解决**，不需要第二套状态。

## 三、🔴 唯一入口守卫（不新增第二个"写 activeFormat"的路径）

| 守卫 | 断言 | 变异（注入坏数据必须报错） |
|---|---|---|
| **o9 · 唯一写入点** | `activeFormat` 赋值全仓**只允许**出现在 `applyFormat` **方法体内**（`methodBodyOf` 切方法体 —— 坑 #4，禁止全文匹配），计数 == **1** | 把赋值复制到 controller → FAIL |
| **o10 · 调用点白名单** | `applyFormat(` 调用点集合 ⊆ {探测路径（现 4 处）+ 用户选格式路径（1 处）}，总数写死比较 | 新增第三个调用点 → FAIL |
| **o11 · 时机守卫** | 新路径必须带"已就绪/已装配"回执判据（不得早于 `addInput`） | 删掉回执判据 → FAIL |
| **o12 · 写完补写手动档** | 该路径里 `applyFormat` **之后**必须有 `reverifyManualIntent` | 删掉 → FAIL |
| **o13 · 能力闸门逐字对应** | Live 判据只允许 `isLivePhotoCaptureSupported`（**负向断言**不得出现近似 API）；置灰矩阵来自设备查询、不得写死 | 换近似 API / 写死矩阵 → FAIL |

> 复用原则：解析 / 排序 / 写入各只有一处实现（查询、复用探测排序、configurator）。

## 四、🔴 单一真源（改哪边 / 怎么同步 / `check_presets` 会不会断）

**结论：批七不改原型、不改 `VideoFormatCatalog` 的静态字面量。**

1. **原型仍做"档位集合 + 占位码率"的真源**：`FMT_BITRATE` 与档位按钮**保持原样**；`state.fmt` 默认 `4K/60` 是原型口径，Swift 默认 `30` 是用户拍板的**既有偏离**（批七不动）。
2. **为什么"码率改读设备真值"不能靠改原型同步**：设备真值随**设备/格式**变、是**运行时**的；原型是静态 HTML，**连"设备能力置灰"都表达不了** ⇒ 改原型既表达不了真机事实，又会把第 5 组弄红。所以走**运行时覆盖层**（先例：ISO 末档 = 设备实读 `maxISO`，而比对表仍收 `12096` —— 同一种做法）。
3. **`check_presets` 第 5 组：不受影响、保持全绿**（它比的是占位表的 12 个值，而占位表不动）。第 6 组（刻度条）与本批无关。
4. **本批**不新增**需要"两边同步"的数据**（档位↔尺寸映射是设备能力查询，属 Swift 侧）；因此**不需要 CB 动作**。若实施中发现非要加"声明式数据"，一律先补原型再动 Swift（老规矩：谁先谁后由 `isSwiftAheadOfPrototype` 标记）。
5. `VideoFormatCatalog` 文件头注释补一句：**占位表 = 声明式基准（脚本比对用）；运行时取值优先实测覆盖**（把语义钉死，防后人误改字面量）。

## 六、真机验收口径（Mac 必验 6 条）

| # | 判据 | 怎么核 |
|---|---|---|
| 1 | 选 **4K/60** → 真的生效 | 日志 `视频格式已应用：4K · 60（applyFormat 1 次，耗时 X.XXs）`；**录一段后读成片分辨率 = 3840×2160**（尺寸是硬证据，不看 UI） |

| 3 | **手动档不被打回自动** | 切格式前后：`ISO/快门/白平衡` 保持 + 出现 `档位复查…已按快照补写` 属**预期内** |

## 七、风险与未验证（诚实边界）

1. **API 未知**（§5 三条）→ 写码前先取证；取证不通过则 R1 降级为 R2/R3，**不阻塞主功能**。
2. **`activeFormat` 变更的手动档影响面**：域变了 → 需补写；若实测发现"补写也压不住"，退路是**切格式时先归一到自动档、再按意图快照重放**（批四"先归一后重放"的老路）。
3. **探测缓存与手动选择的相互作用**（§2.5）是本批最容易出错的地方 → 建议**第一刀不做"落盘为首试目标"**，先做"仅当前会话生效"，把 §2.5 的后半作为**第二刀**（可独立验证）。
4. 本件**未验证项**：`estimatedDataRate` 的可用性、推荐码率 API 存在性、切格式是否伴随黑帧 —— 全部交真机。
