## 四、⑥ 三案对比（**我选方案 3**）

| 方案 | 做法 | 代价 / 风险 |
|---|---|---|
| 1 满宽 fit | 预览按 3:4 满宽缩放，窗内即整帧 → 天然 WYSIWYG | 上下留黑 ≈38% 屏高，**"取景器铺满全屏"的设计意图被改**（那是用户已拍板的设计） |
| 2 满屏 + 成片裁到屏幕可见视场 | 观感不变 | 成片丢 ≈65% 宽度、分辨率与视场大幅缩水 ⇒ **否**（自用拍照 App 不可接受） |
| **3 满屏 + 窗内 WYSIWYG**（推荐） | 背景层保持 `aspectFill`（窗外暗化继续显示取景画面）+ 窗内用 **fit** 渲染 = 成片 | 需**两层预览**；⚠️ **未知点：同一 `AVCaptureSession` 能否挂两个 `AVCaptureVideoPreviewLayer` → 必须真机验证**；不可行则退回方案 1（会动设计意图 → 需二次拍板） |

另建议：无论选哪个，都搭一个「**成片范围提示**」（框外微暗 / 细框），作兜底可读性 —— 即使严格 WYSIWYG 成立，用户也需要知道"按下快门会裁到哪里"。

## 五、⑦ 两方向（**先体检再定，不提前拍死**）

- **方向 A**：压"展开态内容深度"（动 **147 / 144** 两个高度 + `147.0 = 147.0` 恒等式 + "风格名高钉死 13pt"）—— 收益直接，但牵动既有恒等式。
- **方向 B**：不动内容深度，改压**底栏块的其它组成**（图标行 / 间距 / 内边距）—— 风险小，但图标行 **44pt 已卡 HIG 下限**，可能没余量。

**做法**：先让第 12 组⑩ 的净可见账打印**每一块的高度构成 + 各块可压余量**（用现成脚本，不写业务码），拿到真值再选 A/B。
⚠️ 诚实边界：若两个方向都无余量，则本项的修法不是"压高度"，而是**重新设计展开态**（那是设计题，不是几何题）。

## 八、风险与未验证（诚实边界）

1. **⑥ 方案 3 的可行性未验证**：两个预览层能否共用一条 session 是 API 行为问题，本端（Windows）无法验证 → **交 Mac 真机**；不可行则退回方案 1，并需用户对"铺满全屏 vs 严格 WYSIWYG"二次拍板。
2. **⑦ 的可压余量未体检** → 不排除"两个方向都无余量"，届时转设计题（见五）。
3. **P4 分批草案只是骨架**：调整项顺序、LUT 精度、导出色彩、Live/视频的导出口径都要在各自子批开工前单独出方案。
4. 本件**不含任何代码**；批七开工前的第一件事仍是出该批的实施方案（含自检守卫 + 变异测试清单）。
