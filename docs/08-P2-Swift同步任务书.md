### 三.2 顶栏几何：为什么 2-2 必须连带改造模式条（2026-09-17）

顶栏变两行之后，主行的宽度账变了，**模式条放不下了**：

| 形态 | 左 | 中 | 右 | 合计 vs 可用 370pt（iPhone 16 Pro，屏宽 402） |
|---|---|---|---|---|
| 旧（3 项模式条 + 齿轮） | 空占位 38 | 模式条 267.4 | 齿轮 38 | 343.4 ✓ 放得下 |
| 新（4 档模式条 + 三图标）不改模式条 | 电平表 73 | 模式条 **267.4** | 三图标 73 | **413.4 ✗ 溢出 43.4** |
| 新（**改版后的模式条**，字号 13 / 热区 44×44） | 电平表 73 | 模式条 **202** | 三图标 73 | 348 ✓ 两侧各余约 11 |

> ⚠️ **两次数值更正，留档以免再错**：
> ① 最初写「约 150pt / 视觉间距仍是 10」→ 实测是 **179.6pt / 20pt**
> ② 那 179.6 是「字号 11.5 + 每档内边距 5 + `HStack` spacing 10」的产物 ——
> 内边距与 spacing **叠加**了，所以视觉间距是 20 不是 10。
> ③ 2026-09-17 晚按可用性重做后是 **202pt**（字号 13、档间距 18 由内边距产生、
> 每档命中下限 44×44），见下方「三.4」。

**宽度模型（已用两处真机/浏览器实测标定，误差 <1%）**：

```
中文字宽 ≈ 1.0 × 字号        「Log 」≈ 1.97 × 字号（SF Rounded semibold）
档位内容宽 = 各档内容之和
模式条宽  = Σ max(各档内容 + 档间距, 44)      ← 44 是命中下限，取两者较大值
```
标定依据：① 旧版（字号 13、每档内边距 16、档间距 2、外框 3）算得 269.6，Mac 侧实测 **267.4**；
② 11.5pt 那版算得 179.6，与原型浏览器实测（139.6 = 内容 109.6 + 间距 30）**逐项吻合**；
③ 13pt 那版算得 202（44+44+70+44），**待 Mac 侧真机复核**。

溢出 43.4pt 不是"再挤一挤"能解决的：`HStack` 里固定宽的档位不会自己收缩，
结果就是模式条压到右侧图标上（Mac 侧实测过的那种重叠）。

**所以 2-2 含三项几何上必需的改动**（原属模块 #2，现在合并进来）：

1. **模式条去掉胶囊底 + 去掉档位内边距**，字号 13 → 11.5、档间距 10、选中态改
   「白色加粗」（未选中 50% 白）。这一条直接把 267.4pt 降到约 150pt，是能放下的前提；
   顺带把 Swift 侧落后于原型第九轮的观感补上。
2. **「实况」档文字 → 18pt Live Photo 同心圆图标**（复用 2-1b 建的
   `LivePhotoCircleIcon`，一行）：它也是宽度的一部分（文字约 26 → 图标 18）。
3. **命中区补偿**：原型档位 `padding:0`，可点区域只有文字本身（约 23×26pt）——
   真机上偏小。**2026-09-17 晚按 44×44 重做**，见下方「三.4」。

### 三.4 模式条可用性修正（2026-09-17 晚，已交付）

用户复核 2-2 后提出：字号 11.5pt 真机偏小、档位易点错、「实况」档命中区远低于 HIG 44pt。

| 项 | 定案 | 说明 |
|---|---|---|
| 字号 | **13pt**（窄屏 12） | 402 机型能容到 15、390 机型到 14，但 14 在 390 只剩 2.4pt 余量太紧 → 取 13 给窄屏留余量 |
| 命中宽度 | **44 / 44 / 70 / 44** | `max(内容 + 档间距, 44)`；「Log 实况」内容 52pt 本就超 44，热区跟着内容走 |
| 命中高度 | **44** | 行高 30 + **上下各溢出 7pt** |
| 档间距 | **18**（窄屏 12） | 由每档内边距产生；`HStack spacing` 固定 0，**不再叠加** |
| 条总宽 | **202** ≤ 中段 224 ✓ | 两侧各余约 11pt |
| 「实况」档 | 仍只显示图标，**图标 18 → 20** | 加文字要 +30pt → 232 > 224，放不下；图标与 13pt 文字的字重才配得上 |
| 窄屏 | `ViewThatFits` 自动降档 **12pt / 间距 12**（191.6pt） | 375pt 机型中段仅 197pt |

> ⚠️ **「中段 224pt」有一个前提**：主行 `HStack` 的 `spacing` 必须为 **0**。
> 给了 8pt（原型 `.tb-row1{ gap:8px }` 的值），中段就只剩 208pt，393/390pt 宽的机型
> （iPhone 16/15/14）会当场溢出。视觉间距改由两侧块**自己内部的空白**提供：
> 电平表块 73pt 宽但点是左对齐（右边空 23pt）、三图标块 73pt 宽但图标右对齐（左边空 23pt）
> → 模式条两侧实际各有 23 + 11 ≈ 34pt 呼吸空间，与原型 ≈39pt 基本一致。
>
> ⚠️ **375pt 机型上，紧凑版仍是"尽力而为"**：12pt/间距 12 那版是 191.6pt，
> 而中段只有 181pt（343 − 146 − 16），仍超约 5pt —— 但两侧块内部各有 23pt 空白，
> 超出的部分被自然吸收（居中溢出，各 2.5pt），**视觉与命中都不受影响**。
> 四个 44pt 热点 + 「Log 实况」内容的**理论下限是 182.6pt**，所以 375pt 机型上
> 「4 档 + 44pt 亮点」本身就是极限贴合，不存在更优解（除非放弃 44pt 或横向滚）。

**为什么"上下各溢出 7pt"是安全的**（已核算锚点，不是估的）：

- **上溢 7pt** 只到「安全区下沿 + 3pt」—— 顶栏内容距安全区还有 10pt padding
  → 碰不到状态栏，也不会与系统的下拉手势打架
- **下溢 7pt** 落在副行**中段的空白**里 —— 副行只有左右两颗胶囊（约 70 + 72pt），
  中段约 228pt 全空；而模式条热区跨度约 202pt ⊂ 那段空白 → **不抢任何控件的点击**

**优先级（用户拍板）**：触控 44 **不动** > 字号（15→13→12）> 档间距 > 最后才考虑横向滚动。
理由：44pt 是"点不点得中"的功能问题，12 与 13 的字号差异只是"好不好读"的体验问题。

**保留的结构性结论**（记录备查）：三图标若各要 44pt → 单侧 132pt → 中段只剩
`370 − 264 = 106pt` < 模式条 202pt，**差 96pt，必然放不下**。
即「模式条居中可读」与「顶栏三图标各 44pt」在当前布局下**不可兼得**，
要彻底达标只能把模式条拆出来单独占一整行（顶栏变三行，净可见少约 30pt / 3.4%）。
**用户决定：保持两行**，触控问题用上面的溢出方案解决。

> 顺带记一个**还没做、成本很低的备选**：顶栏三图标目前是 24.33×30pt。
> 它们的**下溢方向被堵住**（正下方就是副行的「剩余存储」胶囊，会抢点击），
> 但**上溢方向是空的** —— 所以三图标可以只向上溢出 14pt 拿到 24.33×44。
> 本轮未做（用户限定了实施范围），记为后续可选项。

> **一条几何上的硬约束**（已写进 `Theme.Size.topBarSideWidth` 注释）：
> Apple HIG 建议 44×44pt 触控目标，而顶栏图标只能给到约 24.33×30pt。
> 想做到 44pt 就要单侧 132pt（3×44），中段只剩 370 − 264 = 106 < 模式条 150 → **必然溢出**。
> 「模式条居中」与「三图标各 44pt」在 402pt 屏宽上不可兼得，当前选择是保版式。

## 四、几何规约（重要）

1. **全部相对布局，不写死像素。**
   原型里的 `--fd-size: 246px` / `--fd-center-x: 83.1px` / `--fd-center-y: 662px`
   是**原型侧**的实现手段，Swift 侧**不要照搬数值**。
2. **圆盘圆心对齐「对焦」按钮中心 —— 动态算。**
   原型是从 CSS 推导 `826 −(安全区 18 + 快门 80 + 焦段 44) − 图标行 44/2 = 662`；
   Swift 侧应表达为同样的**相对关系**（用 `GeometryReader` / `alignmentGuide` / `anchorPreference`
   把「对焦」按钮的中心传给圆盘层），而不是写死 662。
3. **圆盘直径的约束**同样相对化：原型口径是"圆盘组（圆盘 + 间距 + 开关行）仍留在屏内"，
   Swift 侧按屏幕可用高度算上限，不写死 246。
4. 尺寸/间距一律走 `Theme.Size`，颜色一律走 `Theme.Palette`。

> ⚠️ 命名空间坑：本项目是 **`Theme.Palette`**（不是 `Theme.Color`）。
> 用某个命名空间前先 `grep -n "enum Palette"` 确认外层容器名 ——
> 曾因凭成员行（`static let canvas = Color.black`）推断而写错 3 处，只有 Mac 编译才发现。
