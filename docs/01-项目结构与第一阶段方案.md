## 1. ⚠️ 云端 Mac 路线的两个真实坑（必须先知道）

### 坑 1：云端 Mac 无法连接你手上的 iPhone

云端 Mac（MacinCloud / MacStadium / EC2 mac 实例）没有物理 USB 通道到你本地的 iPhone。所以：

- ✅ 能编译、能签名、能导出 **IPA**
- ❌ **不能真机调试**（没有 Xcode 调试器、没有 Console 实时日志、没有断点）
- 装到手机上的路径：云端 Mac 导出 IPA → 下载到 Windows → 用 **Sideloadly / AltStore / 爱思助手** 侧载 → iPhone 安装（免费 Apple ID 7 天重签）

**这对一个相机 App 是很大的痛点。** 相机 bug 极多（权限时序、格式不支持、参数越界、预览黑屏），全靠肉眼看现象排障会非常痛苦。

**对策（我会做进工程里）：**
1. `Core/Utils/Log.swift` 用 OSLog 分类记录，**同时写一份到 App 沙盒的 `Documents/lumen-debug.log`**
2. `Core/Utils/DebugHUD.swift` —— 屏幕上的半透明调试浮层，实时显示：当前设备/格式/fps/EV/对焦模式/最近 20 条错误
3. 相机页长按标题 → 弹出「导出日志」，用系统分享把 `.log` 发出来，你在 Windows 上看

> **我的建议**：想办法借一次 Mac（学校机房、同学、网吧级 Mac mini 出租），在前两个阶段做一次真机调试。就一次，能把相机模块的绝大部分坑趟平，后面云端路线就顺了。全程云端会非常耗时间。

### 坑 2：编译反馈回路要提前搭

我在 Windows 上写的代码**无法在本机编译验证**，语法/API 错误一定会存在。所以第一步就要把编译校验搭起来：

**方案：GitHub Actions `macos-15` runner**

```yaml
# .github/workflows/build.yml 骨架
runs-on: macos-15
steps:
  - xcodebuild -version
  - brew install xcodegen && xcodegen generate
  - xcodebuild -scheme LumenEdit -destination 'generic/platform=iOS' \
      CODE_SIGNING_ALLOWED=NO build
```

私有仓库每月 2000 分钟免费额度，macOS runner 按 10 倍计费，即约 **200 分钟实际编译时间/月**，够用。公开仓库无限。

**工作方式**：我写完一个阶段 → push → Actions 编译 → 你把报错贴回来 → 我修。**这是替代「本地编译」的唯一可行回路。**

## 2. 工程基本信息

| 配置项 | 值 | 说明 |
|---|---|---|
| 工程名 | `LumenEdit` | 名字随你改 |
| 工程定义 | `project.yml`（XcodeGen） | `.xcodeproj` 进 `.gitignore` |
| 语言 | Swift 5 语言模式（不用 Swift 6 严格并发） | 严格并发会在 AVFoundation 回调上制造大量误报，稳定后再考虑 |
| 最低系统 | iOS 18.0 | iPhone 16 出厂系统，不写低版本兼容分支 |
| 设备族 | iPhone only，仅竖屏 | 省掉旋转坐标系转换的一整类 bug |
| UI | SwiftUI 为主，相机预览/相机按钮用 `UIViewRepresentable` 包 UIKit | |
| 依赖 | 零第三方 | AVFoundation / Core Image / Photos / PhotosUI / CoreMedia / ImageIO |
| 机型判断 | 一律能力探测 | 设备回退链 + `activeFormat` 能力 + API 可用性，不写字符串 |
| Bundle ID | `com.<你的域名>.lumenedit` | 用免费签名时随便填，唯一即可 |

### 两条架构铁律

1. **分层依赖单向向下**：UI 不直接碰 AVFoundation / Photos，全部经服务层。
2. **`EditRecipe` 是唯一真源**（`Codable`）：同一份参数同时喂给
   - 相机预设注入（`CapturePreset` 派生自它）
   - 修图实时预览（`AdjustmentPipeline`）
   - Live Photo 逐帧（`PHLivePhotoEditingContext` 每帧走同一 pipeline）
   - 视频逐帧（自定义 compositor 走同一 pipeline）

   拍照时把当时的 `EditRecipe` 一并存下，之后在修图页可一键复现同样的配方。这是「取景器看到什么，导出就是什么」的技术前提。

## 5. P1 详细实现方案

### 5.1 交付范围

**做：**
1. 相机 + 麦克风 + 相册 权限申请与拒绝引导
2. `AVCaptureSession` 自建（后置摄像头 + 麦克风），预览铺满全屏
3. 点按对焦（黄色方框动画）+ 同点测光
4. 曝光补偿滑块（EV，-2 ~ +2，1/3 EV 步进）
5. **照片模式**：拍 HEIC，原始数据直存相册
6. **Live Photo 模式**：拍 HEIC + MOV，成对提交为 Live Photo
7. **视频模式**：录 MOV（含音轨），存入相册；录制中红点 + 计时
8. 模式切换条（照片 / Live Photo / 视频），切换时动态重配 output
9. 前后台切换正确停止/恢复 session；录制中被切后台时的安全收尾
10. 屏幕调试图层（DebugHUD）+ 日志文件落盘（应对无调试器）

**不做（明确砍掉）：**
- 人像模式
- ISO / 快门 / 白平衡手动控制（面板留位，P2 填）
- 实时滤镜预览（P4）
- 镜头切换 / 变焦 / 前后摄切换（P2）
- 相机控制按钮轻按的系统滑杆（P2）；**全按快门 P1 就做**
- 导出格式选项、水印、地理位置

### 5.3 关键实现点（为什么这么写）

#### ① 会话配置顺序 —— 你提的坑，落地写法

**根源**：`session.sessionPreset` 一旦设置（或被隐式重置），会话会按 preset 挑格式，把 `device.activeFormat` / `activeVideoMinFrameDuration` 上刚写的手动值冲掉。所以「先配 device 再 addInput」必然失效。

**顺序写死在 `CaptureSessionController.configure()`，注释标明不可调整：**

```
1. session.beginConfiguration()
2. session.sessionPreset = .inputPriority      ← 让会话服从 input 的格式
3. 探测设备（回退链：tripleCamera → dualWideCamera → wideAngleCamera）
4. try AVCaptureDeviceInput(device:)
5. session.addInput(input)                      ← 必须在设 activeFormat 之前
6. 按当前模式 addOutput(...)
7. session.commitConfiguration()
8. 之后才 lockForConfiguration 写 activeFormat / 帧率 / 曝光 / 白平衡
```

第 2 步的 `.inputPriority` 是关键：默认 preset 是 `.high`，它会替你决定格式。切到 `.inputPriority` 后会话完全跟随 `device.activeFormat`。

`beginConfiguration()` / `commitConfiguration()` 必须严格成对，中途任何 `try` 抛错都要保证走到 `commitConfiguration`。

#### ② 硬件参数只有一个出口

`CaptureDeviceConfigurator` 是**唯一**允许 `lockForConfiguration()` 的地方，所有写入都必须：

```
lockForConfiguration → clamp 到设备合法范围 → 写入 → unlockForConfiguration
```

不 clamp 直接写会在真机上抛异常甚至崩（如 ISO 超出 `activeFormat.minISO...maxISO`）。

#### ③ EV 与手动 ISO/快门互斥（P2 要处理）

`setExposureTargetBias(_:)` 只在 `exposureMode == .continuousAutoExposure` 生效；一旦 `setExposureModeCustom(duration:iso:)` 就变手动档，EV 失效。P2 面板需要一个「自动 / 手动」开关。白平衡用 `setWhiteBalanceModeLocked(with: WhiteBalanceTemperatureAndTintValues)`（色温 + 色调，比 RGB gain 直观），gain 必须在 `device.maxWhiteBalanceGain` 内。

#### ④ 点按对焦：手势放 UIKit 层

坐标系转换最容易出 bug。做法：在 `PreviewView` 内部给承载 `AVCaptureVideoPreviewLayer` 的 view 加 `UITapGestureRecognizer` → `gesture.location(in: previewLayer)` → `previewLayer.captureDevicePointConverted(fromLayerPoint:)` → 设 `focusPointOfInterest` + `focusMode = .autoFocus`，同时设曝光点。

写 POI 前必须查 `isFocusPointOfInterestSupported` / `isExposurePointOfInterestSupported`，不支持硬写会崩。

在 SwiftUI 层用 `onTapGesture` 拿坐标还要自己做换算，错位一两像素很常见——**所以手势放进 UIKit 层**。

#### ⑤ 三种模式动态配置 output（扩范围后的核心设计）

不做「所有 output 常驻」，而是按模式增删：

| 模式 | Input | Output |
|---|---|---|
| 照片 | 后置相机 + 麦克风 | `AVCapturePhotoOutput`（`isLivePhotoCaptureEnabled = false`） |
| Live Photo | 后置相机 + 麦克风 | 同一个 `AVCapturePhotoOutput`（`isLivePhotoCaptureEnabled = true`） |
| 视频 | 后置相机 + 麦克风 | `AVCaptureMovieFileOutput` |

**理由**：Live Photo 拍摄与视频录制存在互斥限制，全部常驻很容易出现「某个模式下拍摄静默失败」。切模式时在 `beginConfiguration` 内移除上一个模式的 output、加入新模式的 output，状态清晰。

**注意**：Live Photo 与视频都需要音轨 → session 必须有麦克风输入。麦克风权限也必须在进入这两个模式前拿到。

#### ⑥ Live Photo 拍摄与成对落盘 —— 最容易翻车的一块

**拍摄：**

```swift
let settings = AVCapturePhotoSettings(from: template)
let url = FileManager.default.temporaryDirectory
    .appendingPathComponent("live-\(UUID().uuidString).mov")
settings.livePhotoMovieFileURL = url        // ★ 每次必须唯一，复用同一 URL 会失败
settings.livePhotoVideoCodecType = .hevc
photoOutput.capturePhoto(with: settings, delegate: self)
```

**两个回调顺序不保证：**

- `photoOutput(_:didFinishProcessingPhoto:error:)` → `photo.fileDataRepresentation()` + `photo.resolvedSettings.uniqueID`
- `photoOutput(_:didFinishProcessingLivePhotoToMovieFileAt:duration:photoDisplayTime:resolvedSettings:error:)` → MOV URL + `resolvedSettings.uniqueID`

**配对逻辑（`LivePhotoAssembler`）**：用 `[Int64: PendingLivePhoto]` 按 `uniqueID` 暂存，两边到齐才提交。**任何一边先到都必须等**，不能直接保存——这是最常见的 bug：先存了照片，等 MOV 到了再补，结果系统里就是「一张静态图 + 一段孤立视频」。

**提交：**

```swift
PHPhotoLibrary.shared().performChanges {
    let req = PHAssetCreationRequest.forAsset()
    req.addResource(with: .photo, data: heicData, options: nil)
    req.addResource(with: .pairedVideo, fileURL: movURL, options: nil)   // ★ 同一个 request
}
```

**必须同一个 `PHAssetCreationRequest`、必须成对**，否则「照片」App 不会识别成 Live Photo。

**临时文件清理**：成功提交后删除 MOV；**失败路径也必须删**，否则 tmp 目录会越堆越大。

#### ⑦ 视频录制

- 用 `AVCaptureMovieFileOutput`（P1 最简方案；P6 做逐帧滤镜时才会换成 `AVAssetWriter` 路线）
- 录制目标 URL 每次唯一
- `movieFileOutput.connection(with: .video)?.videoRotationAngle = 90`（竖屏固定值）
- 录制中禁止拍照，UI 上把快门按钮变成停止按钮
- `didFinishRecordingTo` 回调里检查 error，把文件搬进相册（`.video` 资源）
- **录制中被切后台**：`stopRecording()` 并保证已录部分能落盘；这条必须真机测

#### ⑧ 音频会话（`AudioSessionManager`）

```swift
try session.setCategory(.playAndRecord, mode: .videoRecording, options: [.defaultToSpeaker, .allowBluetoothA2DP])
try session.setActive(true)
```

- 只在视频 / Live Photo 模式激活；回到照片模式或退出相机页时 `setActive(false)`
- 不激活 → 视频没有音轨；激活了不释放 → 会一直占用音频资源，其它 App 播放异常、也更耗电

#### ⑨ 拍照保存：原始数据直取

```swift
let settings = AVCapturePhotoSettings(from: template)   // init(from:) 复制配置，你提的用法正确
settings.flashMode = .off
settings.maxPhotoDimensions = photoOutput.maxPhotoDimensions   // iOS 16+ 取代 isHighResolutionCaptureEnabled
```

拿到 `photo.fileDataRepresentation()` 的原始 HEIC 字节，直接 `PHAssetCreationRequest.addResource(with: .photo, data:)`。

**为什么**：绕开「解码 → 处理 → 重编码」，画质无损、最快、EXIF 与色彩配置全保留。P4 应用滤镜后才走 `PhotoExporter` 重编码。

**两个细节：**
- iOS 17+ 的 `isAutoDeferredPhotoDeliveryEnabled` 建议显式设为 `false`。开着时 `fileDataRepresentation()` 可能返回代理图，表现为「保存的图变糊」。
- iPhone 16 Pro 4800 万像素需要把 `photoOutput.maxPhotoDimensions` 与 `settings.maxPhotoDimensions` 都设成格式支持值。P1 用默认值，P2 再开并实测耗时。

#### ⑩ 线程与生命周期

- `startRunning()` **绝不能在主线程**，全放专用串行队列 `DispatchQueue(label: "capture.session")`
- `didEnterBackground` → `stopRunning()`；`willEnterForeground` → 检查 `isRunning` 后 `startRunning()`
- `AVCaptureVideoPreviewLayer.session` 赋值要在 session 配置之后，顺序反了会先黑屏一次

#### ⑪ 方向：锁竖屏，固定 90°

`AVCaptureConnection.videoRotationAngle`（iOS 17+，替代废弃的 `videoOrientation`）在竖屏下固定 90°。因为 App 只支持竖屏，这个值不用动态计算——**这一条省掉后面 Live Photo 和视频导出的一整套方向修正逻辑**。

#### ⑫ 色彩空间：现在定好，避免 P4 返工

iPhone 拍出来是 **Display P3**，Core Image 默认工作空间是线性 sRGB。不处理会在 P4 出现「预览偏色、导出更偏」。约定写进 `ColorSpaces.swift`：工作空间用 `extendedLinearSRGB`，输入保留原始配置，输出显式写 P3 或按需转 sRGB。

#### ⑬ 相机控制按钮 —— 我明确标注不确定的地方

iOS 18 给第三方两层能力：

1. **全按 = 快门**：`AVCaptureEventInteraction`（iOS 17.2+），加到承载预览的 UIView 上，全按 `.began` 触发。**P1 做这个。**
2. **轻按 = 系统滑杆**：iOS 18 的 `AVCaptureControl` 体系（`AVCaptureSlider` / `AVCaptureIndexPicker` / `AVCaptureSystemZoomSlider` / `AVCaptureSystemExposureBiasSlider`）+ `AVCaptureSessionControlsDelegate`。轻按相机按钮时系统在按钮旁渲染你注册的控件。**P2 做，挂载 API 以 Xcode 16 SDK 为准——我无法在本机编译确认。**

**其他不确定项：**
- 相机按钮在 App 非前台时能否唤起本 App：**系统限制，大概率不行**，本方案只做前台接管
- 该交互对象没有公开的「当前设备是否有相机按钮」判断（据我所知）→ **不写机型判断**，无脑挂上，无按钮的设备上它就是不触发，优雅降级

#### ⑭ 性能基线

- 预览用 `AVCaptureVideoPreviewLayer`（系统零拷贝通路），CPU 开销极低；**不引入** `AVCaptureVideoDataOutput`
- 视频 P1 固定 1080p30 或 4K30，不做 4K120（P6 再谈，且逐帧处理 4K120 只能离线导出，不可能实时）
- 存储提示：4K30 视频约 350MB/分钟，Live Photo 约 3~4MB/张。DebugHUD 里显示剩余空间
