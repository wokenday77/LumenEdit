## 一、① 刻度条复刻飓风（方案 A · 用户拍板）

### 1.1 精度依据（**唯一真源已换**）

用户 2026-09-21 补的飓风 ISO/快门条**全分辨率截图**（1206×2622 = **402pt @3x**，精确到 0.3pt）实测：

| 量 | 飓风实测 | 我们旧口径 | 现在 |
|---|---|---|---|
| **tick pitch（档距）** | **120px = 40.0pt**（逐根等距，最大偏差 0.3pt） | ISO 46 / 快门 56 / WB 26 | **统一 40pt** |
| **刻度高 / 宽** | 42px = **14.0pt** / 4px = **1.33pt**，**每档同高** | 五档层级 22/15/10/6.5 | **单档 14 / 1.33** |
| **选中刻度** | 66px = **22.0pt**（向上 +8pt）+ 加宽 2pt + **绿** | 三角指针 12×8 + 竖线 1.5 | **选中档加高加宽变绿** |
| **档间细刻度** | **无**（细:主 = **1:1**） | 批五加了第 5 档 `hair` | **删** |
| **每档标签** | **每档都有** | 只有 `labelAt` 标出的档 | **全标签**（字号维持 10.5） |
| 选中档标签 | **不放大、不变色** | — | 同左 |
| 标签底 ↔ 刻度顶 | **39px = 13pt** | 数字距底 2pt | **13pt** |
| 可视档数 | 8~9（滚动式） | — | **8~9（接受）** |

**两条重大结论（当时与批五方向有张力 → 用户拍板 = 方案 A）**：

1. **"细:主高度比"的答案是 1:1 —— 飓风压根没有细刻度。** 每档一根 14pt 等高刻度 + 每档一个标签，
   只有选中档会长高（22pt 绿）。批五加的 `hair` 档是照旧 contact sheet 推的，**与全分辨率实测不符**。
2. **"slot 压到 18~20pt"与"全标签"不可兼得** → 二选一：
   (a) **复刻飓风** = 40pt 档距 / 子集档位 / 全标签 / 无细刻度；　(b) 保留全档 + 细刻度 = 18~20pt / 只有少数档带标签。
   **用户选 (a)**，并**接受代价**：每条条只看得见 8~9 档、要滚动。
   复算是自洽的：402pt 屏、gutter 64pt → 可视 (402−64)/40 = **8.45 档**，与飓风的"8~9"吻合。

⚠️ **作废口径（别再引用）**：旧 `reference/video-frames-2026-09-16`（contact sheet，588px ≈1.5px/pt）推出的
「WB 主档间 9~10 条细刻度 / 细:主 1:2 / 主档 18pt」，以及建立在它上面的**批五 `hair` 五档验收口径**。
`docs/22` 里"刻度细分"那节保留为历史记录，但**验收以本件为准**。

### 1.2 落地参数（**逐令牌可复算** —— 文档只贴脚本打印的数）

| `paramStripTickWidth` | **1.33** | 刻度宽（飓风 4px） |

→ 选中刻度顶（自顶量）= `84 − (25.5 + 22)` = **36.5pt**；气泡底（自顶量）= **22pt** → **余 14.5pt**（自检第 19 组打印同值）。

`LumenEdit/Presets/ParameterStripCatalog.swift`：

| 条 | 档数 | 档位表 | 备注 |
|---|---|---|---|
| ISO | **25** | 50…**12096**（约 1/3 档等比） | 末档 = **设备实读 `maxISO`**：标称表收在 12096，运行时再由 `isoValues(deviceISOMax:)` 按当前设备覆盖（只替换末档，档数不变 → 比对口径不漂） |
| 快门 | **42** | 1 → 1/8000，**补全 1/3 档** + 影院值 `1/96`、`1/120`，**删 `1/12000`** | 最慢档标签是 `"1"`（不是 `"1s"`） |
| 白平衡 | **76** | 2500…10000 步长 100 | 预设 5 档 `[3000,4000,5200,6000,7500]` 保留**琥珀色**刻度，但**高度与普通档相同**（飓风没有层级） |

- **指示器**：选中刻度（22pt + 加宽 2 + 绿）自己承担指示；气泡固定在可视区中点、不接收触摸；
  选中判据用 `currentStepIndex`（按显示值吸附到最近档）—— **与气泡同源**，硬件回读值（如 ISO 934）不落档位时两者必须指向同一档。
- **颜色优先级**（顺序有讲究）：`自动态 / 不可用档`（整条压暗）→ **选中档（绿）** → 预设档（琥珀）→ 普通。

### 1.3 三处取舍（**说清理由，别当 bug 复报**）

1. **删 `1/12000`**：行业表没有它；且在 40pt 档距 + 全标签下它是 7 字符（≈43pt）**必然与邻档叠字** ——
   用户给的三个选项里选了"去掉"。
2. **ISO 末档不扩到 12800**：用户此前在飓风截图里看到的 `12096` **就是设备实读 `maxISO`**（我们日志实锤同值），
   不是 12800。改"末档显示设备实读上限"比把表扩到 12800 更忠实硬件（12800 大概率在设备 maxISO 之外 → 扩了反而置灰）。
3. **档数差 5 倍靠滚动消化**：一个档距走三条 → WB 76 档 = 一条 3040pt。这是方案 A 的**已接受代价**。

### 1.4 🔴 遗留风险（**Mac 复验请实测一眼**）

按源码真值复算（脚本按 `estimatedLabelWidth` 的估算式：数字 0.62em / 字母 0.68em / `/` 0.42em / `.` 0.30em，字号 10.5）：

| 条 | 档数 | 最宽标签 | 估算宽 | 距档距 40pt 余量 |
|---|---|---|---|---|
| 快门 | 42 | `1/1000`（6 字符） | 36.96pt | 3.04pt |
| ISO | 25 | `10000`（5 字符） | 32.55pt | 7.45pt |
| **白平衡** | 76 | **`10000K`（6 字符）** | **39.69pt** | **0.31pt** ← 🔴 |

> 自检第 19 组会把这条打成 **"最宽那档估算宽 ≈39pt、距档距仅 1pt，属『2pt 余量』红线"**（取整口径）。
> **估算 ≠ 实测**：项目纪律里"中文字宽按 1.0em 推、**拉丁/数字必须实测**"依旧成立 ——
> 静态自检只用来挡住"明显要叠"，**白平衡 5 位数 + K 这档必须真机看一眼是否会碰**。
> 若真碰：备选是白平衡标签去掉 `K`（`10000` → 32.55pt）或降到 10pt 字号 —— **等 Mac 实测结论再定，本端不动**。

## 二、② 冷启动预热（修 4.27s 静止帧）

### 2.1 根因（先定性，再动手）

复验实测「刚进 App 点对焦 → **4.27s 静止帧**」。那 4.27s = **每设备首次换设备的冷探测**
（12~41 个候选逐个 `applyFormat`，每个 300~800ms）；而"点对焦"会先触发**预切换**（打开对焦盘 → 静默挂物理设备），
所以这 4s 正好发生在用户眼皮底下。

那 4.27s 的画面是**静止帧**（预览层在 input 重挂期间保持最后一帧，批五已说明 —— **不需要**额外"冻结"机制），
观感 = 卡住/像转场。**真正要做的只有一件事：把 4s 从用户操作路径挪到启动后的空闲时间。**

### 2.2 为什么必须用**独立私有会话**

直播路径挑格式依赖 `photoService.output.isLivePhotoCaptureSupported`，而**一个 output 只能属于一个会话**
（直播会话此刻挂着虚拟多摄）→ 预热只能自带一个独立会话 + 一次性 `AVCapturePhotoOutput`
（**与直播路径同一个 API** 判 Live 能力），挑完整体拆掉。

### 2.3 实现要点

| 点 | 做法 | 为什么 |
|---|---|---|
| 队列 | `prewarmQueue`（`DispatchQueue(qos: .utility)` 串行） | 预热要跑 4~5s，**绝不能占 `sessionQueue`**（那条队列还要服务点按 / 切档） |
| 时机 | 会话 `.running` 之后，**延后 1s** 再动 | 先把"会话启动 + 首帧"让过去，别和启动抢设备 |
| 范围 | **只预热 `photo` / `livePhoto`**；只探**缓存里没有的**；按设备 `uniqueID` 逐颗去重 | 缓存 key = `设备|模式`；预切换只发生在照片/实况下 |
| 前置 | `guard state == .running, !form.isPhysical` | 已经在物理形态 / 未就绪时不必探 |
| 缓存属主 | **字典的唯一属主是 `sessionQueue`** —— 预热队列只算不写（`sessionQueue.async` 里写 + `persistFormatProbeIdentities()`） | 防数据竞争 |
| 探测 | `prewarmProbe`：私有会话 `beginConfiguration` → `canAddInput/canAddOutput` → `addInput/addOutput` → `commitConfiguration` → `startRunning()` → 逐候选 `applyFormat` 直到 `isLivePhotoCaptureSupported` | **必须真跑起来** Live 能力才是真值（与直播路径同源） |

### 2.4 三层兜底（**这是本条的"不影响正常使用"保证**）

1. **`canAddInput` / `canAddOutput` 为假就跳过** —— 设备被占用（排他性）时直接放弃这一颗，不硬上。
2. **`wasInterruptedNotification` 一到 → 立刻拆预热 + `prewarmAbandoned = true`（本次运行内不再试）**
   —— 唯一能确认"预热没搞坏主链路"的信号就是"直播会话有没有被打断"；真被打断宁可没有预热也不能黑屏。
   观察者在 `startRunning()` **之前**挂上（否则第一枪漏看）。
3. **开关可关（A/B 用，不必重出构建）**：`-lumen.camera.prewarm.disabled YES`（启动参数）/ `defaults` 同名键。

### 2.5 边界与代价（诚实写清）

- 探不到就返回 `nil`（`try?` 建 input 失败 / 试完所有候选都没有 Live 格式 / 无候选）→ **只是"这次没预到"**，
  后台真用时会走完整探测，**不会让链路更坏**。
- 预热期直播会话若被系统打断（用户切走了 App / 来电等**非预热原因**），同样会触发兜底 → 表现为"本次运行内预热已放弃"，属预期。

### 2.6 复验口径（Mac）

`预热开始：待探 N 颗（…）` → `预热探到格式：<镜头> <格式>（候选 N 个）` → `预热结束：耗时 X.XXs`；
A/B：`-lumen.camera.prewarm.disabled YES` 时应见 `预热跳过：开关已关（…）`，且回到 4s 冷探测（**对照组**）。
若见 `⚠️ 预热导致直播会话被打断 → …本次运行内不再预热` = **闸门兜住了**（同时预览**不该**黑屏）。

### 2.7 ⚠️ 本端无法验证的硬约束（前一轮就是因此没敢做）

**"同一颗物理设备只能属于一个会话"**：私有会话去挂虚拟多摄的 constituent，**可能**让直播会话收到
`AVCaptureSessionWasInterrupted`（`.videoDeviceInUseByAnotherClient`）→ 预览黑屏。
`docs/22` 一② 因此把 ② 推迟了一轮，本轮由用户点名要求做 → 用**串行 + `canAddInput` 预检 + 打断即弃**三层兜底换风险，
**但"到底会不会打断"只有真机能答**。这条是批六里**风险最高、最需要 Mac 优先验的一条**。

## 三、③ 点按对焦按意图重放（「不选自动就永远手动」· 已完成，留档口径）

**系统语义（根因）**：`setFocusAndExposurePoint` 把 `exposureMode` 设成 `.continuousAutoExposure`
→ 手动 ISO / 快门**被顶掉**。旧口径是"重发真值让 UI 立刻回到自动"，那等于 **App 自己替用户退出手动档**。

**现口径**：**点按只是"重新对焦"，不是退出曝光手动的意图** —— 点按前取意图快照、点按后按快照重放
（与切模式 `switchMode` 同一套写入）：

| 路 | 写入 | 日志 |
|---|---|---|
| ① 曝光 | `setManualExposure(iso:seconds:)` ← 快照 | `点按对焦后按意图重放手动曝光（ISO … / …）` |
| ② 白平衡 | `setManualWhiteBalance(temperature:tint:)` ← 快照 | `点按对焦后按意图重放手动白平衡（…K）` |
| ③ EV | 只在**快照本来就是自动曝光档**时重放 | `点按对焦后按意图重放 EV（…）` |

- ⚠️ **顺序有讲究**：先把系统设的连续自动曝光**按快照写回 `.custom`**，**最后**才推 EV
  —— `applyExposureBias` 见 `.custom` 会回切自动档（`docs/16` 第五节那条防线）。
- 收尾：`publishManualState` + 一行 `点按对焦后档位：曝光=… / 白平衡=… / 意图=…`（Mac 核法）
  + `reverifyManualIntent(2, …, reason: "点按对焦复查")` 两拍复查（500/800ms，系统可能在 AF 收敛前后**再改一次**）。
- **与方案 A 不冲突**：方案 A 解「手动**对焦**」这条轴（点按 = 重新对焦 + 解除手动对焦，防"无出路"）；
  本条保**曝光 / 白平衡**两条轴。
- **"仅测光"路径（`setExposurePointOnly`）不需要本套**：它自带 `device.exposureMode != .custom` 守卫，本来就不碰手动档。

## 四、④ 掉帧资源埋点（**产出是"可定性的证据"，不是"已修好"**）

### 4.1 判据（Mac CB 初判 · 用户场景）

用户场景：**开所有功能 → 切手动 → 依次切 照片/实况/log/视频 后掉帧；重启 App 立刻恢复。**
判据：热降频 / 系统节流**不会**因重启 App 快速恢复；App 侧资源泄漏（模式切换 / 静默预切换没拆净的 input/output）
**会随次数累积、重启清零**。用户口的原文是「**B 操作后顿**」，按此方向查。

### 4.2 逐点计数（**漏埋一次 = 计数错，比没有更坏**）

11 处裸调用全部紧邻埋点：`session.removeInput`(796) / `addInput`(804) / 回滚 `addInput`(810) /

### 4.3 资源账三件套

| 件 | 做法 | 为什么 |
|---|---|---|
| `refreshResourceSummary()` | 读活数 `session.inputs.count / outputs.count`，与该模式**预期**（`expectedResourceCounts` = 录制类 2 / 其它 1 个 input、1 个 output）比较，**超出即 `DebugLog.warn("⚠️ 资源超出预期（多出来的那个就是泄漏的形状）：…")`** | 比"累计增删对不上"**更早**报出来 |
| `memoryFootprintMB()` | `task_info(TASK_VM_INFO).phys_footprint` | **不用 `resident_size`**：它含可回收页，内存涨了它常常不动 → 读不出泄漏。取不到返回 `nil`（**诊断信息绝不影响主链路**） |
| 5s 周期账 | `snapshotTick % 5 == 1` → `sessionQueue` 上重算并打一行 `资源：模式 … · input 活 N（累计增/删 a/b）· output 活 N（…）· 内存 NMB` | 只在增删时打日志**看不到"没增没删但内存一路涨"** |

### 4.4 耗时入日志（同一批补齐）

- `换设备完成（转场 / 静默·无转场）→ …；耗时 X.XXs`（`performFocalSwitch` 是**换设备的唯一执行体**，转场/静默两条路都过它 → 两边耗时可比）
- `静默换形态耗时 X.XXs`（命中缓存 ≈0.3~0.8s；**每设备首次冷探测 4~5s**）
- `切模式耗时 X.XXs`（切模式 = 重配 outputs + 可能的 input 增删，**泄漏头号嫌疑路径**）

### 4.5 对称性审计结论（**说清"没找到"**）

对 `reconfigure` / `performFocalSwitch` / `switchMode` / 清理路径做了增删对称性审计：
**结构上没找到泄漏**（每次 `addInput` 都有配对的 `removeInput` 或明确的所有权转移）。
→ 所以本条的产出是**把"活的有几个、增删对不对得上"变成日志里一眼可读的数字**，
定性要靠 Mac 按复现脚本跑出来的计数 + 内存曲线 —— **不预设结论、不假装修好**。

### 4.6 复现脚本（Mac）

开所有刻度条 → 切手动 → **照片 / 实况 / log / 视频 依次切 ×N 轮**，然后看：
- `input 活 N / output 活 N` 是否随轮次**单调上涨**（不回到基线 = 泄漏实锤）；
- `内存 NMB` 是否只涨不落；
- 是否出现 `⚠️ 资源超出预期`。
