# 05 - 协作流程（Windows 开发机 + Mac 验收机）

> **重要前提更正**：CodeBuddy 也装在 Windows 上，不是装在 Mac 上。
> 也就是说：**手上两个 AI 助手都编译不了 iOS**。编译这件事不能指望 AI，得指望 GitHub Actions 和 Mac。
> 本文档按这个真实前提重写。

---

## 一、角色表（先认清谁在哪、谁干什么）

| 角色 | 在哪 | 干什么 | 干不了什么 |
|---|---|---|---|
| **主笔** WorkBuddy（老弟） | Windows | 架构决策、写全部 Swift 代码、文档、滤镜预设、网页原型、修编译错误、静态自检 | 编译不了 iOS |
| **审查者** CodeBuddy | Windows | 独立视角审查（找编译风险 / 运行时崩溃 / API 误用）、联网核对 Apple 文档 | 编译不了 iOS；**不改代码，只出报告** |
| **编译机** GitHub Actions | 云端 macos-15 | 无人值守自动编译校验，push 即触发 | 跑不了真机（无摄像头） |
| **验收机** Mac | 桌面（主人手动） | **唯一能做真机验收的地方** | 没有 AI 助手在上面 |

**一句话结论**：iOS 编译回路靠 Actions（自动）+ Mac（兜底），**不靠任何一个 AI**。两个 AI 的价值是「写」和「审」，不是「编译」。

---

## 二、唯一桥梁：GitHub 仓库

- 仓库里只有源码 + `project.yml` + 文档 + 原型，**`.xcodeproj` 不入库**（XcodeGen 本地生成）→ 两边永远不会因工程文件冲突打架。
- 分支：自用项目直接用 `main`，不搞 PR / review 流程。
- **push 纪律**：每完成一个自检通过的可编译单元就 push，不攒大批量。批越大，报错越难定位。
- 如果 `github.com` 直连不通（本机有过这种情况）：先确认代理是否开着，`git push` 能走通就说明通道没问题。

---

## 三、主回路：GitHub Actions 自动编译（无人值守）

这是**整个流程里最关键的一环**——它替代了「Mac 上有个 AI 帮你编译」这个不存在的角色。

```
① Windows：老弟写码 → tools/check_swift.js 自检 → git push
② GitHub Actions（macos-15）自动跑：xcodegen generate → xcodebuild
   ├─ ✅ 通过 → 进第 ③ 步
   └─ ❌ 失败 → 主人把失败日志贴给我 → 我修 → push → 回到 ②
③ Mac：git pull → xcodegen generate → Xcode 打开 → 真机验收
```

**首次启用要确认的**：
- 仓库 Settings → Actions → General → 确认 Actions 已启用（新建 repo 默认开启）；
- 打开 `https://github.com/<你的用户名>/<仓库名>/actions` 看有没有跑起来；
- 公开仓库 Actions 分钟数无限，不用心疼。

**从 Actions 拿日志**（两选一）：
- 网页：点进失败的那次 run → 点红色 ✗ 的步骤 → 复制日志；
- 命令行：`gh run list` 找 run id → `gh run view <id> --log-failed`。

---

## 四、Mac 的角色：只做真机验收

Mac **不需要 AI 助手**在上面干活，主人手动跑就行。步骤见 `README.md` 第三节，六步：装 Xcode 16 → `brew install xcodegen` → clone → `xcodegen generate` → 配签名（改 Bundle ID + 选个人 Team）→ ⌘R。

**只有 Mac 真机能验的东西**（Actions 编译通过 ≠ 功能正常）：
- 相机预览画面、对焦方框位置是否准
- 拍照 / Live Photo 成对落盘、相册里是不是真的 Live Photo（不是静态图+孤立视频）
- **相机控制按钮**（两处待验证 API，见交接单）
- 触觉反馈、发热、帧率、录制时长、存储空间提示

Mac 上发现问题 → 描述现象 + 复现步骤 + DebugHUD 最后几行（HUD 有 200 条环形日志，现场数据都在）→ 回传给我修。

**易断环节**：新文件加了忘跑 `xcodegen generate` → 报 `cannot find 'XXX' in scope`，先查这个别先怀疑代码；签名报错九成是 Bundle ID 没换。

## 五、CodeBuddy 的位置：对抗性审查者（可选，不是回路必需）

CodeBuddy 的价值**不在于重复我干的活**，而在于它**不知道我的思路**——所以能发现我自以为对的地方。它的上下文跟我完全隔离，这是我给不了的第二意见。

**用法**：我交付一批代码后（git 提交完），让它做一次独立审查，**只出报告、不改代码**。它发现的真问题我采纳，误报我驳回。

**给 CodeBuddy 的审查提示词（复制即用）**：

```
你是 iOS 代码审查员。项目 LumenEdit 是纯 Swift/SwiftUI 的 iOS 18 相机 App，
零第三方依赖，用到 AVFoundation + Core Image + Photos + PHLivePhotoEditingContext。

先读 docs/04-交接单.md 和 README.md 了解背景。

任务：审查 LumenEdit/ 下全部 Swift 文件，只输出问题报告，不要修改任何文件。
重点找这四类问题：
1. 会导致编译失败的地方（API 签名过时、可用性标注缺失、类型不匹配、Swift 6 并发隔离问题）
2. 会导致运行时崩溃的地方（强制解包、数组越界、main 线程约束、delegate 生命周期）
3. Apple API 用法错误（参数含义搞反、回调时机理解错、必须成对调用的没配对）
4. 逻辑漏洞（状态机缺分支、错误路径没清理资源、竞态）

特别优先核对这两处（我标注为"待 SDK 确认"，无法离线验证）：
- CameraControlButton.swift 中 AVCaptureEventInteraction 的初始化签名
- AVCaptureEventInteraction 是否遵循 UIGestureRecognizer（有没有 isEnabled）

硬性要求：
- 每条问题必须给出：文件:行号 + 问题描述 + 依据（Apple 官方文档链接，或明确说明"基于经验，未查证"）
- 不确定的必须标注"不确定"，禁止编造 API 名称和签名
- 按严重程度排序：编译失败 > 崩溃 > 行为错误 > 风格建议
```

**注意**：CodeBuddy 默认可能会直接改代码，**必须明确禁止**。它一改，我和它的改动就会打架。

## 六、防打架规矩（两个 AI 在同一台机器上，最容易出的事）

**铁律：同一时刻只允许一个 AI 在改 `LumenEdit/` 目录。**

原因：两个 agent 同时改同一份文件，后写的会静默覆盖先写的，而且两边都不知道，仓库直接乱。

正确节奏：

```
我写码 → git commit（明确提交信息）→ 交棒
         ↓
CodeBuddy 只读审查 → 输出报告（不改文件）→ 交棒
         ↓
我按报告修 → git commit → 下一个循环
```

- 交接的锚点是 **git 提交记录**，不是"口头说改完了"；
- 主人当调度员：谁在干活就说一声，另一个等着；
- CodeBuddy 若必须改代码（比如验证一个修法），**先让它另开分支或 `git stash`**，改完把 diff 给我看，由我决定是否合入。

## 七、报错回传格式（Mac / Actions → Windows）

```
[错误 N]
来源: Actions 日志 / Xcode Issue Navigator / 真机现象
文件: LumenEdit/Camera/Hardware/CameraControlButton.swift
行号: 42
报错: <原样复制完整一行，含 error 前缀，不要自己总结>
上下文: <做了什么操作>
```

- **编译错误**：原样全文，别转述成"编译失败了"；
- **真机问题**：现象 + 复现步骤 + DebugHUD 最后几行 + 截图；
- 不完整的报错等于让我猜，会多耗一轮。

## 八、可选增强：在 Windows 上装 Swift 工具链（优先级低，看清权衡再决定）

**能做的**：Windows 有 Swift 官方工具链（`winget install Swift.Toolchain`），理论上可以用 `swiftc -parse` 做**语法层**检查，比现在手写的 `tools/check_swift.js`（只做括号配平）强。

**代价（已查证）**：
- 必须先装 **Visual Studio C++ Build Tools + Windows SDK**，官方安装说明标注占用 **6–8 GB**；
- 磁盘现状紧张（四盘合计约 86GB 可用）；
- 已知限制：Windows 上 `swift` REPL 不可用、`swift run` 行为异常需改用 `swift build`、`swiftc` 要手动带 `-sdk %sdkroot%`；
- **最关键**：`swiftc -parse` 到底能不能解析 `import UIKit`/`AVFoundation` 的 iOS 代码，我**没有实测条件，不能保证**（Windows 上根本没有 iOS SDK；`-parse` 只做词法+语法解析、不做模块解析，理论上可行，但需实测确认）。

**权衡结论**：**暂时不建议装**。GitHub Actions 已经在真正的 macOS + iOS SDK 环境下免费自动编译，能力远强于 Windows 上的语法检查，而且不需要付出 6-8GB 和半小时。等哪天想要「不联网、push 前的秒级本地反馈」，再考虑。

## 九、护栏：不许动的地方（速查）

- `CaptureDeviceConfigurator` = 唯一 `lockForConfiguration()` 入口；
- `PhotoLibraryWriter` = 唯一相册入库入口；
- `PhotoCaptureService` 持有全项目唯一一个 `AVCapturePhotoOutput` 实例；
- 会话配置顺序不可调整（`beginConfiguration` → `.inputPriority` → addInput → addOutput → `commitConfiguration` → 之后才写 `activeFormat`/帧率）；
- Live Photo 必须同一 `PHAssetCreationRequest` 内 `.photo` + `.pairedVideo` 成对提交；
- 照片保存走 `fileDataRepresentation()` 原始字节直存；
- UI 层不允许直接调用 AVFoundation / Photos，必须走服务层；
- `EditRecipe`（P4 引入后）= 修图参数唯一真源；
- 五条硬性技术纪律全文见 `docs/04-交接单.md` 第六节。
