## 一、问题 1 的一笔账（"要很用力"其实不是力度问题）

iPhone 16 Pro（402×874，安全区 778）：

```
顶部：顶栏 56 + 外层 padding 10                                    = 66
底栏栈：EV 面板 108 + 16 + 图标行 44 + 16 + 焦段条 44 + 16 + 快门排 80 + 内边距 10  ≈ 334
→ 底栏栈上沿落在安全区 y ≈ 778 − 10 − 334                          ≈ 434

而 #7 的起点线 = 0.55 × 778                                        = 428
可用起手带 = 428 ~ 434                                             = 6pt
```

**结论**：起点落在 y < 428（取景器中部及以上）完全不响应；落在 434 以下又被底栏控件吃掉。
用户偶尔成功的那几次，是手指正好落在底栏各行之间的 **16pt 行距空隙**上
（VStack 的 spacing 区没有视图，触摸会穿透到取景器）。

### 参数对照表（改前 → 改后）

| 参数 | 改前 | 改后 | 理由 |
|---|---|---|---|
| `swipeActivationDistance`（起手门槛） | 24 | **10** | 24 是原型在浏览器里定的（鼠标/触屏双环境）；10 是 SwiftUI 默认量级，响应更跟手 |
| `swipeMinTravel`（位移阈值） | 34 | **18 → 16** | 34pt ≈ 3.4mm，且 24pt 起手门槛之后才算，合计要滑 5.8mm 才认；第二轮反馈"还是要用力"后再降一档 |
| `swipeMaxDuration`（时长上限） | 0.8s | **1.2s** | 起点时刻记在"起手门槛之后"，0.8s 实际更紧；慢滑（很常见）被拒就是"要很用力"的体感来源之一 |
| `swipeStartRegionRatio`（起点线） | 0.55 | **0.25** | 见上面的账；改后只排除最上面 25%（顶栏 66pt + 调试浮层区） |
| 横向排除 | `\|dx\| ≤ \|dy\|` | `\|dx\| ≤ \|dy\| × 1.5` | 斜着上滑很常见，原型口径（斜一点就拒）在真机上太严 |

**改后的可用起手区**：底栏栈降到 ≈ 210（参数排收起）→ 上沿 ≈ 558；
起手只要 `y > 0.25 × 778 ≈ 195` 且**在取景器可见区内**（`y < 558`）即可
→ 可用带从 6pt 变成约 **363pt**。

> 保留的判定：**从底栏控件上起手的拖动仍然不触发**（EV 滑条 / 横滑条 / 药丸 / 快门 / 图标按钮）
> —— 这不是靠排除清单，而是靠**结构**：那些控件在 ZStack 里绘制在上，触摸被它们吃掉，
> 根本到不了挂在预览层上的手势。落在底栏**行距空隙**上的起手会被正常接受。

## 二、问题 2 / 3 的方案：参数排默认收起，图标行「曝光补偿」是开关

### 依据（原型，不是自创）

```
.row-params{ height:44px }                          ← 常态只有一行
.screen.strip-on .row-params{ height:140px }        ← 点「曝光补偿」才展开
.row-params .params-closed-bar{ order:1 }           ← 图标行在上
.row-params .strip-panel{ order:2 }                 ← 刻度/滑块面板在下
原型第二轮定稿：「参数排收起态不再点整行展开 —— 只有点「曝光补偿」才展开滑块」
```

Swift 侧此前把 `ExposurePanel` **无条件渲染**（常驻），是对原型的偏离；图标行那一格又只弹
toast（"在上方参数排调节"），于是用户既关不掉、也找不到何处关。

### 落地

| 项 | 做法 |
|---|---|
| 新状态 | `CameraViewModel.isExposurePanelExpanded`，**默认 false**（不落盘，临时手势状态） |
| 开关入口 | 图标行第 6 项「曝光补偿」→ `exposureCompensationTapped()` = **toggle**，展开时 toast 报当前 EV 值、收起时提示可再展开 |
| 渲染门控 | `CameraView.isExposurePanelShown`（= 展开 && 非放大态）；参数排与图标行**顺序对调**为原型顺序（图标行在上、面板贴其下） |
| 互斥（三方向） | 展开参数排 → 收滤镜条 / 场景·风格；展开滤镜条或场景·风格 → 收参数排。下划的 `collapseOverlays()` 一次收起三个 |
| ⤢ 放大态 | 参数排强制隐藏（状态保留，与滤镜条同规则） |

> 这一条同时**补齐了 `CONTEXT_HOT` Backlog ④** 里"浮层互斥缺一半"的洞
> —— 之前 `collapseOverlays()` 只有两个浮层，现在三个，且注释写明"新浮层必须加进来"。

### 顺带的收益：常态净可见回到 50% 以上

| 状态 | 改前 | 改后 |
|---|---|---|
| 底栏栈高 | ≈ 334 | ≈ 210（−124） |
| 取景器净可见 | 778 − 66 − 334 = **378 ≈ 43%**（**低于 50% 底线**） | 778 − 66 − 210 = **502 ≈ 57%** ✓ |

> 产品约束"净可见永不低于 50%"在参数排常驻时其实是**被破的** —— 这次一并修掉。

## 三、问题 2 的另一半：EV 滑条竖向落手也会改值

`ParameterSlider` 用的是 `DragGesture(minimumDistance: 0)`（为了点哪跳哪的手感），
后果是**任何落手都会被滑条接管**：用户在参数排上竖向滑动（想上滑呼出浮层），
滑条按"手指当前的 x"算 EV → **EV 直接跳到那个位置的值并写进硬件**。
体感就是"曝光补偿条一直在干扰"。

**修法：方向闸门**（`ParameterSlider` 内，通用控件，未来的 ISO / 快门 / 白平衡刻度条同样受益）

- 落手后累计位移不超过 **6pt** 的死区 → 不判方向、不改值
- 判出来**横向为主**才接管；竖向为主（含斜向但不是横向为主）→ **整个拖动生命周期都不碰值**，
  也不发 `onEditingChanged`（不会触发 `setExposureBias`）
- 判定只做一次（`isHorizontalDrag`），拖动中途反向不会反复横跳

## 四、风险与回退点

| 改动 | 风险 | 回退 |
|---|---|---|
| 手势五个参数 | 太松会把"斜着滑"也当呼出 → 误呼出浮层 | 五个常量集中在 `CameraView` 一处，改回 24/34/0.8/0.55/1.0 即可 |
| 参数排默认收起 | 用户可能找不到 EV 在哪调 → **已有 toast 明确指路**（"点「曝光补偿」可再次展开"），且那一格本来就是 accent 高亮 | `isExposurePanelExpanded` 初值改 `true` 即回到常驻 |
| 参数排与图标行顺序对调 | 展开态外观变化（面板从"图标行上方"变到"下方"） | 交换两段顺序即可；对齐原型 `order` 是本次的依据 |
| `ParameterSlider` 方向闸门 | 极端斜向拖动可能被误判为不接管（用户需重滑） | 死区与判据是两个显式常量；将来真有反馈可改成"按主轴接管 + 横向补偿" |

"展开浮层时收起刻度条/圆盘"仍缺这两项 —— 落地时加进 `collapseOverlays()`（注释已留位）。

## 五、第三轮：横拖 EV 误触发下划（2026-09-18 复验抓到的回归）

> 第二轮修正的复验结果：★ 核心项全过（起手落在滤镜条上的第二次上划 ✅、滑到一半就有反应 ✅、
> EV 13 档 ✅、两条 UX 留痕 ✅），但抓到**一个由第二轮改动引入的新回归**。

**现象（真机日志实锤）**

```
12:39:29      参数排展开（开始横拖 EV）
12:41:13.381  [ui] toast: 已收起参数排      ← 横拖中途被误判成"下划"，面板当场收起
12:41:13.921  已呼出滤镜条                  ← 用户只能重新上划
```

**根因**：第二轮把手势挂到**整页 ZStack**（修"第二次上划"）+ 改成**提前触发**（修"僵硬"）
→ 横拖 EV 时手指的**自然纵向抖动**只要累计到 16pt，就在起手阶段命中了"下划"。
`ParameterSlider` 自己的方向闸门拦不住它 —— 那道闸门只管"滑条不接管"，
**父级的整页手势是并发识别的**（`simultaneousGesture` 语义如此）。

**修法：两道闸门（都留着，覆盖不同场景）**

| 闸门 | 内容 | 覆盖 |
|---|---|---|
| ① **精确** | `!viewModel.isExposureEditing` —— EV 滑块拖动期间整页手势禁言（`exposureEditingChanged` 此前**吃掉了 `isEditing` 参数**，编辑态从未被记录，这次补上） | EV 滑块 |
| ② **通用** | **方向锁**：一次拖动只在最初 6pt 定一次主轴，之后不再改判；起手横向 → 全程不参与呼出/收起 | 横拖 EV **以及**横滑滤镜卡条 / 场景胶囊条等（不依赖"谁在拖动"，未来新增控件自动受益） |

> 为什么不只做闸门①：它依赖控件把"编辑态"报上来 —— 横滑条那类控件（ScrollView）没有这个通道，
> 同类误触会在那里复发。方向锁是**不依赖控件配合**的兜底，且是 iOS 手势识别的通行做法。

**顺带确认**（用户问的"同一个口子一并堵"）：闸门加在判定处，**上划与下划共用同一条路径**，
所以横拖时的纵向抖动**两个方向都不会再触发**。

## 六、Mac 截图 / 真机验收清单

### 第二轮真机反馈后的三个修正（2026-09-18 · 必读）

> 第一轮的修复**不足以**解决真机问题，第二轮反馈把 ③ 的根因挖出来了 —— 是个**结构缺陷**。

#### ③ 上划两次只能呼出一个（根因 · 最关键）

**现象**：第一次上划呼出滤镜条 ✓，**第二次上划无反应**，呼不出场景·风格（于是④没法验证）。

**根因：手势挂载点错了。** 第一轮把手势挂在 `previewLayer` 上，理由当时写的是
"底栏是绘制在上的兄弟视图，落在它上面的触摸到不了手势，这正是我们要的排除效果"——
**这个理由在"第一次呼出"时无害，在"第二次呼出"时致命**：

```
第一次上划：滤镜条还没显示 → 屏幕下部那块是取景器 → 手势收到 ✓
            呼出后，滤镜条（144pt + 16 行距）插进底栏栈顶部
            → 它占掉的正是用户上次起手的那块区域
第二次上划：手指落在同一位置 → 触摸落在滤镜条（标题行 / 横滑卡条 / 面板）上
            → 被它们吃掉 → previewLayer 的手势收不到 → 无反应 ✗
```

**修法**：把手势从 `previewLayer` 移到 **`cameraContent` 的整页 ZStack** 上，仍用
`simultaneousGesture`。这样落在**任何子视图**上的拖动都能被同时识别：

| 落点 | 结果 |
|---|---|
| 滤镜条 / 场景·风格条的面板、卡条、标题 | **能呼出 / 收起** ✓（③ 的修复） |
| 横向 ScrollView（卡条）上的竖向拖动 | 能呼出 ✓（横向拖动由 `\|dx\| ≤ \|dy\| × 1.5` 排除，不影响横滑） |
| 按钮（图标行 / 药丸 / 快门 / ⤢） | 能呼出 ✓；按钮自身的 tap 不会误触发（移动后 tap 本就失败） |
| EV 滑条上的竖向拖动 | 能呼出 ✓（滑条的方向闸门不接管，两者不冲突） |
| 顶栏区域（y < 25%） | 不触发（起点区排除，保留） |

> ⚠️ **若真机上"从卡条上起手"的第二次上划仍不灵**（理论上横向 UIScrollView 的 pan
> 识别器在竖直方向会失败并放行，但需真机确认），备用方案是：在滤镜条面板**底部留一条
> 24pt 全宽的手势带**（内容深度 129 ≤ 144，本来就有 15pt 富余，把它做成无子视图的空白带）——
> 触摸落到那里必经 ZStack，几乎必然有效。

#### ① 上滑僵硬：除了阈值，还有一个"必须松手才生效"的问题

第一轮只放宽了阈值，但判定放在 `onEnded` —— 意味着**必须滑到位并松手**才有反馈。
用户滑到一半看不见任何变化，会以为没反应，于是滑得更用力更快 → 这就是"僵硬、要用力"的体感来源。

**修法**：判定移到 `onChanged`，**滑够阈值立刻生效**（不等松手），并用 `swipeDidTrigger`
保证一次拖动只跨一级（否则一次长滑会直接从滤镜条跳到场景·风格）。
位移阈值同时 18 → **16pt**。

#### ② EV 吸附不明显：不是吸附算法的问题，是**范围**的问题

查了 `ParameterSlider`：吸附逻辑（`roundedToStep(step)`）+ 过档触觉（`Haptics.tick()` =
`UISelectionFeedbackGenerator.selectionChanged`）**都是对的**。真正的问题是范围：

```
设备范围 minExposureTargetBias...maxExposureTargetBias = -8…+8（iPhone 实测口径）
16 EV ÷ (1/3 EV) = 48 档
滑条可视宽 = 402 − 2×16（外层） − 2×16（面板） ≈ 338pt
→ 每档 7pt：手指一动跨好几档，吸附完全感知不到
```

**修法**：新增 `Float.evUIRange = -2...2`（系统相机的口径），滑条范围取
**「UI 范围 ∩ 设备范围」**（`ClosedRange.intersected(with:)`，遇到窄范围设备就用设备的）。
→ **13 档、每档约 28pt**，档位感清晰。
硬件安全不受影响：`setExposureBias` 里仍按设备真实范围 clamp。
附带收益：写硬件的频率降到原来的 1/4（每档一次）。

1. **上滑灵敏**：从取景器中下部轻滑一下 → 滤镜条升起；**滑到一半就有反应**（不必松手）

12. 常态净可见 ≥ 50%（参数排收起后应明显变大）
13. **EV 触觉（第四轮定稿：滞后 0.75 档 + 节流 150ms）**：
    **慢拖每档一响清晰可数**；**快扫一段只响 2~3 声**（改前约 17 声/秒连成一片）；

    斜着上滑仍能呼出（横向裕度 1.5 未动）；慢滑（1 秒以上）仍被接受（时长上限 1.2s 的验证点）

## 七、第四轮：两个"敏感度"微调（2026-09-18 · 方向相反的两件事）

### ① 曝光补偿条触觉太密（"拉到部分数值时一直触发咔"）

**查证结果**（用户问的三点，逐条回答）：

| 问 | 答 |
|---|---|
| 是不是每跨一档都触发？ | 是 —— `if snapped != value { value = snapped; Haptics.tick() }` |
| 有没有节流？ | **原本没有**（已补 55ms） |
| 档位间距 28pt 是不是太密？ | **不密**：13 档 ÷ 338pt ≈ 28.2pt/档，是 iOS 常规量级。密的是**边界判定** |

**真因**：档位边界是**一个点** —— 手指停在某个边界附近（= 用户说的"部分数值"）时，
亚像素抖动让 `roundedToStep` 在相邻两档之间反复翻转，"值变了 → 响一下"于是每帧成立。

**修法（两道，都做）**：

1. **滞后换档**（`hysteresisRatio = 0.6`）：与**连续索引**比距离，离当前档位不到 0.6 档就不换档
   —— 边界从"一个点"变成"一段过渡带"，停在边界上不再是来回换档。
   手感代价：数值比手指位置滞后 0.1 档 ≈ 2.8pt，察觉不到。
2. **触觉节流**（`tickThrottle = 55ms`）：第二道保险，快速来回拖动时不至于连成一片振动。
   `resetToDefault()`（点数值归零）的触觉**保留** —— 那是明确的一次操作。

顺带修一处次序问题：`onEditingChanged?(true)` 移到"是否换档"判定**之前** ——
否则手指小幅移动（未跨档）时编辑态不上报，`isExposureEditing` 闸门不生效。

### ② 上下划太敏感（"想稍微降低敏感度"）

**逐条回答**（其中一条是误分类）：

| 参数 | 改前 | 改后 | 理由 |
|---|---|---|---|
| 起手门槛 | 10 | **14** | 推迟"进入判定"的时机；**不影响响应速度**（位移阈值 20 > 14，滑够时早已进入判定） |
| 位移阈值 | 16 | **20**（≈2mm） | 演进：34 → 18 → 16（第一轮"太严"）→ **20**（第三轮"太灵"）。20 能成立的前提是**方向锁**已拦掉横滑类误触 |
| 时长上限 | 1.2s | **保持 1.2s** | ⚠️ **它不是敏感度参数，而是宽容度参数** —— 它是"超时不算滑动"的上限，调小只会排斥慢滑，正是第一轮修掉的"要很用力" |
| 方向锁死区 | 6 | **10** | 主轴判定更明确，减少"起手那一下还没定性"的模糊期 |

> 时长这一条是本次分析里最有价值的判断：**三个候选参数里有一个方向上搞反了** ——
> 手感问题要区分"敏感度"（阈值类，双向可调）与"宽容度"（上限类，只能放宽）。

**自检同步改为区间守卫**：早先只守"不许太严"（单向上限）→ 结果放宽过头。
现在两端都守：起手 8~16 / 位移 **18~32** / 起点线 0.1~0.35 / 方向锁死区 6~14，
外加"触觉必须走滞后 + 节流、且不得绕过节流直接 `Haptics.tick()`"。

### ③ 复验后的二次调参（Mac 实测：**机制对、量不够**）

Mac 侧复验的一句话结论很准：机制生效了，但**两个量级都太小**。

| 项 | 第一版 | 复验判定 | **定稿** | 依据（Mac 实测账） |
|---|---|---|---|---|
| `hysteresisRatio` | 0.6 | ✅ 这层有效（过渡带 0.2 档） | **0.75** | 过渡带收窄到 0.25 档容差，抗边界抖动更强 |
| `tickThrottle` | 0.055s | ❌ **形同虚设** | **0.15s** | 匀速拖 100pt/s 时**每 288ms 跨一档**，55ms 窗口完全拦不住 → 快扫约 **17 声/秒**（连成一片）。0.15s → 快扫最多 **6.7 声/秒**（一段快扫通常 2~3 声）；慢拖每档 >0.15s **照响，零精度损失** |
| `swipeMinTravel` | 20pt（≈4.4mm） | ❌ 仍在敏感侧（预期 5~6mm） | **28pt**（≈6.2mm） | 落在 34（僵硬）与 16（过敏）的**中间偏硬**处 |
| 起手门槛 / 时长 / 起点线 / 横向裕度 | 14 / 1.2s / 0.25 / 1.5 | ✅ 不动 | 不变 | 时长那条的纠正已确认 |

**两条可复用的判据**（写进自检，防止"机制在但量形同虚设"）：

1. **触觉节流的量级必须与"每档耗时"同量级** —— 短于约 1/4 档耗时的节流等于没做
   （55ms vs 每档 288ms 就是这么失效的）。自检现在要求 `tickThrottle ≥ 0.1s`、`hysteresisRatio ≥ 0.7`。
2. **"每跨一档必响"本身是正确设计**（棘轮手感），要治的不是密度而是**快扫时的频率** ——
   别去动档位间距（28.8pt 是正常量级），去调节流。

**复验口径**（改完后 Mac 侧一句话验证）：
① 慢拖 EV 每档一响清晰可数 → ② 快扫一段只响 2~3 声 →
③ 上划需要明确的一下（约 6mm），斜滑 / 慢滑不受影响。
