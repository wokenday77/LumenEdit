## 零、结论：诊断成立，是个**反馈环路**，不是常量问题

用户的三条查证，逐条给证据：

### ① `exposureBias` 有没有被回写？→ **有，而且没有守卫**

`CameraViewModel.attach()` 第 184-187 行：

```swift
// 硬件侧读回来的曝光补偿 → 同步到滑块
environment.session.$exposureBias
    .receive(on: RunLoop.main)
    .sink { [weak self] value in
        self?.exposureBias = Double(value)      // ← 无任何编辑态守卫
    }
    .store(in: &cancellables)
```

**这就是环路的回边**：滑条改值 → 推硬件 → 硬件值发回来 → **又写回滑条的值**。

### ② 拇指位置渲染自哪个值？→ **全部渲染自 `value`**（这条不是问题）

`ParameterSlider`：

| 元素 | 渲染源 |
|---|---|
| thumb 位置 | `thumbCenterX(width:)` → `normalized(value)` |
| 填充条 | `thumbCenter`（同样派生自 `value`） |
| 数字 | `valueFormatter(value)` |

→ **不存在"thumb 跟手指、fill 跟 value"那种不同步**。真正的问题是：
**`value` 本身被外部（硬件回写）擅自改写** —— 渲染源被第三方覆盖。

### ③ 拖动期间挂起回写？→ **必须挂，现在没挂**（这就是修法）

## 一、环路时序（为什么会产生"跳动"）

```
手指移到档位 N+1
  ↓
滑条 value = N+1                       （主线程，立即）
  ↓ onEditingChanged(true) → setExposureBias(N+1)
sessionQueue.async { ... }              ← ① 异步队列
  ↓
configurator.applyExposureBias          ← ② withLock(device)，可能等锁
  ↓
publish { self.exposureBias = N+1 }     ← ③ 若在队列上 → DispatchQueue.main.async
  ↓
@Published 变化
  ↓
attach 的订阅 .receive(on: RunLoop.main) ← ④ 再经一次 RunLoop
  ↓
viewModel.exposureBias = N+1（几拍之前的值）
  ↓
SwiftUI 重算 → thumb / 填充 / 数字**按旧档位重画**
```

**四段异步**（队列 + 锁 + main.async + RunLoop）累加出可感知的延迟。拖得快时，
`viewModel.exposureBias` 被写回的是**几拍之前**的值 —— 于是：

- 视觉：thumb 被"拽回"旧档位
- **更糟**：下一次 `onChanged` 里，**滞后判定是以被拽回的值（旧档）为基准**重新算的
  → 同一个档位边界被**重复跨越** → 触觉又响一次

→ 这解释了为什么"加了滞后仍在连响"，以及**为什么滞后比越大、跳动越明显**：

> 滞后比越大 → 换档点越靠后（0.75 档 vs 0.6 档）→ 被拽回后"重新跨过"的距离越大、
> 越容易再次满足换档条件 → **振荡被放大**。

用户的"对比值敏感"推理精确命中了这一点：**纯密度问题不会对滞后比值敏感**。

## 二、修法

### 主修法（用户第 ③ 条）：拖动期间挂起回写

```swift
environment.session.$exposureBias
    .receive(on: RunLoop.main)
    .sink { [weak self] value in
        guard let self else { return }
        // ⚠️ 拖动期间**不回写**：硬件回写要走 sessionQueue + 设备锁 + main.async + RunLoop，
        // 到达时已是"几拍之前"的值 —— 会把滑条拽回旧档位，并在滞后判定里被当成基准，
        // 造成"反复跳动 + 重复跨档触发触觉"（见 docs/14）。
        guard !self.isExposureEditing else { return }
        self.exposureBias = Double(value)
    }
```

**"松手后以最终吸附值为准同步一次"是自动成立的**，因为
`exposureEditingChanged(_:)` 里是**先复位 `isExposureEditing`、再推硬件**：

```swift
func exposureEditingChanged(_ isEditing: Bool) {
    if isExposureEditing != isEditing { isExposureEditing = isEditing }   // ← 先复位
    environment?.session.setExposureBias(Float(exposureBias))            // ← 再推（松手那一下会回写一次）
}
```

### 加固（建议同时做）：丢弃"队列里积压的旧值"

拖动中每档推一次硬件，`sessionQueue` 会按序回放。松手那一刻 `isExposureEditing` 已复位，
于是**队列里还没跑完的旧值会被依次回写** → 表现为"松手后值回放式跳一下"。

修法：只接受**与最后推送值一致**的回写（硬件把最新值发回来才算数）：

```swift
private var lastPushedExposureBias: Float?
// 推硬件时记录
lastPushedExposureBias = Float(exposureBias)
// 回写时比对
guard let sent = lastPushedExposureBias, abs(Double(sent) - Double(value)) < 0.001 else { return }
```

并在**会话重建 / 模式切换**时把 `lastPushedExposureBias` 置 `nil`（那种场景下硬件值来自
设备而非我们推送，必须允许回写）—— 复用它已有的 `session.$mode` 订阅位置。

> 为什么需要加固：不加它，主修法只解决了"拖动中"，**拖动尾部与松手瞬间仍有回放窗口**。
> 队列积压通常只有 1~2 个（每档 288ms 一次 vs 处理 <10ms），所以回放很轻 ——
> 但用户已经在为"跳动"较真，这一下也该堵掉。

### 可选（本次不做，记账）

**拖动中节流硬件写入**（如每 100ms 最多一次 + 松手补一次）：能进一步减少队列积压与硬件写入。
代价是拖动中画面变化略滞后。等真机上确认 EV 实时性有余量再说。

## 四、验收口径（真机）

1. **拖动中**：thumb / 填充 / 数字**单调跟随手指**，不出现"被拽回"
2. **快拖到底再拖回** → 无振荡、无"来回抖"
3. 触觉：慢拖每档一响；**不出现"同一档位重复响"**
4. **松手后**值稳定，不出现回放式跳变
5. **功能不退化**：切模式（会话重建）后回来，UI 值与硬件一致（说明回写仍有效）
6. 点数值归零 → 硬件跟随（回写未被永久禁掉）
