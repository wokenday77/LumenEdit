## 二、架构改造：按焦段挂载物理设备（第二步施工图）

### 2.1 为什么必须换

虚拟多摄的三条手动能力全被 SDK 关死（上表）。选 **方案 A（物理设备）**：拍手动参数时，
会话挂载的是**物理单摄**，能力探测全为 true，手动档全部可用。

### 2.2 焦段 → 物理设备映射

| 焦段档 | 挂载设备 | 说明 |
|---|---|---|
| 13mm | `builtInUltraWideCamera` | 原生视场 |
| 24mm / 35mm / 48mm | `builtInWideAngleCamera` | 35/48 = 主摄数码裁切（沿用 `FocalPreset.mainCropFactor`） |
| 120mm | `builtInTelephotoCamera` | 原生视场 |

- 回退规则沿用 B1 的镜头探测（`CaptureCapabilities.hasUltraWideLens / hasTelephotoLens`）：
  没有那颗镜头的机型，对应档位照旧置灰（灰但仍可点，点了给原因）。
- **自动档模式不强制切物理设备**：纯取景 / 自动曝光 / 自动白平衡下，虚拟多摄的平滑变焦体验更好。
  **何时切物理**：① 用户进入任一手动档（ISO/快门、白平衡、手动对焦）；② 或统一策略
  "物理设备会话常驻"（见 2.6 拍板点 ①）。

### 2.2b 回切策略（2026-09-19 Mac 预检 ① · WB 拍板，Mac/用户可否决）

**进手动切物理，回自动也切回虚拟** —— 否则进过一次手动就永久失去平滑变焦（B1 的成果报废）。

- **切入**：任一手动档激活（ISO/快门手动、白平衡手动、对焦手动）→ 切物理（模态转场，见第三章）。
- **切回**：全部手动档都退回自动（`manualExposure == nil && manualWhiteBalance == nil && 对焦非手动`）
  **持续 2 秒（防抖）→ 切回虚拟**。
  - 防抖理由：用户常"快速试一档手动再回自动"，立即切回会来回打摆（每次都是一次换设备 +
    转场）；2s 是"确认离开手动"的最小静默期（量级与"试一下"的手部动作周期同档，自检⑫守
    `∈ [1, 5]s`）。
  - 切回同样走模糊转场；自动态无需参数搬运（各参数本来回的是自动档）。
  - 防抖计时起点 = 最后一个手动档退出时刻；期间再进手动则取消计时。
- 实现位：`CaptureSessionController`，防抖计时器只在 sessionQueue 逻辑上判断（时间戳比较，不另起 Timer）。

### 2.3 跨切换点换设备流程（如 24mm → 120mm）

> **顺序按 Mac 预检 ⑥ 修正**：参数搬运**必须在 `applyFormat` 之后**（clamp 依赖新设备的
> `activeFormat`，而那是 commit 之后才写的 —— 原稿"搬运写在 begin~commit 内"违反铁律 1，
> clamp 拿到的是旧格式甚至默认格式的范围）。

```
sessionQueue 上串行执行：
0. 前置条件（见 2.3b）：
   - ramp 进行中 → 先 cancelVideoZoomRamp() 再继续
   - 会话未就绪（state != .running）→ 记 pendingFocalSwitch，startInternal 就绪后补执行
   - 录制中 → 拒绝（toast，见 2.7）
1. 发布 isLensSwitching = true（UI 先淡入模糊，见第三章 ⑧ 顺序触发）
2. beginConfiguration
3. removeInput(旧物理 input)
4. addInput(新物理 AVCaptureDeviceInput)
5. commitConfiguration
6. applyPreferredFormatLocked(新设备)   ← 写 activeFormat / 帧率（铁律 1：commit 之后）
7. 参数搬运（见 2.4；此刻新 activeFormat 已定，clamp 有真依据）
8. 发布 isLensSwitching = false（UI 淡出模糊）+ publishManualState(新设备)
```

与 `buildSession()` 同款幂等与顺序纪律；`.inputPriority` preset 不变。

#### 2.3b 前置条件细则（Mac 预检 ②）

| 场景 | 处理 |
|---|---|
| 旧设备 `rampingVideoZoom == true` | 先 `configurator.cancelVideoZoomRamp()`（唯一锁内），再走换设备流程 |
| 会话未就绪（`state != .running`） | **排队**：记 `pendingFocalSwitch`（档位 id），`startInternal()` 就绪分支里补执行 —— 不做"点了没反应"，toast 说明"相机就绪后切换" |
| 换设备请求已在执行中 | 直接忽略重复请求（模态转场期间焦段条本来已禁点，这里是兜底） |

### 2.4 参数搬运边界（Mac 报告结论 + 预检 ④⑤ 修订，逐条接住）

| 参数 | 能否搬 | 做法 |
|---|---|---|
| ISO / 快门 | ✅ | 两颗设备都支持 `.custom`；**在 `applyFormat` 之后**（预检 ⑥）clamp 到**新设备 activeFormat** 的范围再 `setExposureModeCustom`（越界抛异常，铁律 2） |
| 白平衡 | ✅ | 物理设备支持锁定增益；初值取**旧设备当前色温**（`currentTemperature(of:)`，冷启动兜底 5600K 那套已就位），色调跟随新设备当前值；**搬运顺序同样在 `applyFormat` 之后** |
| **EV 补偿（预检 ④ 补）** | ✅ | `exposureTargetBias` 是**每设备属性** —— 不搬的话换设备瞬间亮度跳变 + UI 的 EV 显示与硬件不一致。做法：clamp 到新设备 bias 范围后 `setExposureTargetBias`；EV 仅在自动曝光档生效，若同时搬 ISO/快门（手动档）则 EV 本来被系统忽略，**先搬曝光、EV 值原样保留在 session 状态**（回自动档时自动恢复生效） |
| **对焦（预检 ⑤ 修订：显式降级，不搬运）** | ⚠️ 降级 | 每颗镜头 `lensPosition` 物理量程不同，旧值搬过去**必然对不上焦**。策略：**显式降级为连续自动对焦** + toast「已切换镜头，对焦回到自动」+ 日志留痕 —— 不假装手动档还在（"落回连续自动"与"用户仍处手动对焦档"是矛盾的，取显式降级；对焦圆盘 UI 回到自动态，B3b 落地时由硬件真值回读驱动） |

### 2.5 变焦重做（B1 语义变化）

- 物理设备没有 ramp 跨镜头：**同镜头内**仍可 `videoZoomFactor` 平滑（数码），**跨切换点 = 换设备**，
  `videoZoomFactor` 直接赋值 → 画面**会跳一下**（系统级行为，掩盖手段见第三章转场）。
- **物理路径的档位 → zoom 映射自建表（Mac 预检 ⑦）**：`nativeZoomLadder` 吃的是虚拟切换点数组
  （`virtualDeviceSwitchOverVideoZoomFactors`），**物理设备下为空数组 → 现有 `zoomFactor(forFocal:of:)`
  会失效**。物理路径不查阶梯，按"档位 → 已挂载的那颗镜头"直接给：

  | 档位 | 挂载镜头（2.2） | 物理路径 `videoZoomFactor` |
  |---|---|---|
  | 13mm | UltraWide | **1.0**（原生视场） |
  | 24mm | WideAngle | **1.0**（原生视场） |
  | 35mm | WideAngle | **1.0 × 1.458**（`FocalPreset.mainCropFactor`，数码裁切） |
  | 48mm | WideAngle | **1.0 × 2.0**（同上） |
  | 120mm | Telephoto | **1.0**（原生视场） |

  ⚠️ **比例不抄第二份**：35/48 的系数必须从 `FocalPreset.mainCropFactor` 真读（与虚拟路径同源），
  自检⑩守"物理映射表不得出现字面量 1.458 / 2.0"。实现为 `zoomFactor(forFocal:of:)` 的**物理分支**
  （按当前会话挂的是虚拟还是物理分派，收敛在 `CaptureCapabilities` 一处）。
- `applyZoomRamp`（B1 那套）保留给虚拟设备会话；物理会话下焦段条点击走"换设备 + 模糊转场"，
  条内拖动（若有）走数码 zoom。两条路径由**当前会话挂的是虚拟还是物理**分派，收敛在
  `CaptureSessionController` 一个入口，不散在 UI。
- 自检第 11 组"切镜头路径只做 lock→ramp→unlock（无 beginConfiguration / input 增删）"这条守卫
  **要改**：物理路径恰恰要 begin/commit + input 增删 —— 改成"虚拟路径不得增删 input；
  物理路径的增删只能在 `CaptureSessionController` 的换设备方法里"。

## 三、模糊转场（补充需求 · 方案 B · 已拍板推荐）

**目的**：掩盖物理设备切换瞬间的预览黑屏、参数跳变、对焦偏移 —— 飓风相机同款"模糊→清晰"。

### 3.1 实现（**顺序触发** · Mac 预检 ⑧ —— 替代原稿"并发 + 时长与切换耗时同源调参"）

- **挂载点**：`PreviewView`（已是 `UIViewRepresentable` 包 `AVCaptureVideoPreviewLayer`）
  内部叠一个 `UIVisualEffectView(effect: UIBlurEffect(style: .regular))`，盖满预览层。
  **不参与任何相机逻辑**，纯视觉浮层。
- **驱动**：分层纪律 —— 会话层不碰 UI。会话只发布
  `@Published private(set) var isLensSwitching = false`；**换设备的发起权在 UI 时序手里**：

  ```
  ① 用户点焦段（跨切换点）→ VM 请求 → UI 把模糊淡入（0 → 1，0.15s）
  ② 淡入完成（动画 completion）→ 才调 session.applyFocalPhysical(...)
  ③ 会话换设备 + 搬参数（2.3 全流程）→ 完成后发布 isLensSwitching = false
  ④ UI 收到 false → 模糊淡出（1 → 0，0.25s）
  ```

  为什么改顺序触发：原稿"动画时长与切换耗时同源调参"要求**并发**跑转场与换设备，
  时长必须人工对齐实测耗时 —— 慢了露黑屏、快了白糊。**顺序触发下模糊在切换开始前就已
  完全盖住画面**，切换快慢都不影响观感，两个动画时长变成纯视觉常量（0.15/0.25，自检守量级），
  **没有"匹配"这个概念了**。
- 两个时长做成 `Theme` 令牌（`evLensBlurIn 0.15 / evLensBlurOut 0.25`），量级守卫 `∈ [0.1, 0.5]s`。
- **B3a 的 EV 圆盘 toast 抬升已用同款"模糊盖住再动"思路**（toast 进圆盘层），风格一致。

### 3.2 约束与**验收要点（预检 ⑨：说清"糊的是什么"）**

- **峰值段糊的可能就是黑**：`removeInput → addInput → commit` 之间预览可能黑几帧 ——
  转场打开时糊的是**当时画面**，若那几帧恰好落在黑屏上，用户看到的是
  **清晰 → 糊 → 黑一瞬 → 糊 → 清晰**。这是**预期行为不是 bug**：转场的目的是**软化**跳变
  （让黑屏/跳变不再是"啪一下"），不是**消灭**它。验收口径见第五节，别当回归打回。
- 转场期间**禁点**焦段条（防连点叠两个换设备流程）；录制中本来就不给切。
- 转场是**纯 UI**：不加进 `collapseOverlays()`（它不是"扩展浮层"，没有互斥语义）。
